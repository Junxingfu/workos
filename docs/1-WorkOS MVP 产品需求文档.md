# 冻结与变更规则（V1\.3\.5）

本文档从 V1\.3\.5 起冻结为 **MVP 产品需求基线**。

"冻结"指的是：

```Plain Text
产品定位 / 用户画像 / 核心问题   已冻结
核心对象与领域模型              已冻结
Item 状态机 / Task·Note         已冻结
Waiting / Follow-up             已冻结
Today / Inbox / Daily / Context 已冻结
Reminder                        已冻结
用户维护成本原则 / 默认行为矩阵   已冻结
```

**不冻结**的部分：

```Plain Text
页面具体交互   → 原型验证阶段可调整（文档 5）
API 形状       → 技术设计阶段可调整（文档 2/6）
DB 字段        → 技术设计阶段可调整（文档 3/4）
UI 像素细节     → 原型验证阶段可调整
Tauri 实现      → 技术设计阶段（文档 4）
```

## 允许修改的 5 种情形

```Plain Text
1. 明确的需求矛盾（两份文档互相打架）
2. 明确的逻辑漏洞（规则之间无法同时成立）
3. 用户可用性测试发现的阻断问题
4. 安全 / 数据一致性问题
5. 实现过程中发现的不可行性
```

## 不允许作为修改理由的 6 种说法

```Plain Text
1. "以后可能有用"
2. "竞品有这个功能"
3. "感觉应该有"
4. "顺便做一下"
5. "用户以后可能需要"
6. "AI 可以顺便做"
```

处理方式：

```Plain Text
以上 6 类诉求一律进入 V1.1 / V2 Backlog
不修改 MVP 基线
```

## 冻结以后的工作模式

```Plain Text
冻结前：

冻结后：
  发现问题 → 讨论"现有能力能不能顺畅完成" → 改原型 / 交互
```

>
> 来源：一份企业真实场景的"用户一天工作旅程"（含项目经理 / 产品 / 研发 / 测试 / 加班 / 临时插入）。
>
> 那份文档里的绝大多数解法（AI 自动总结、会议自动上下文、跨系统关联、消息聚合）
> 属于我们明确排除的 AI / 集成 / 团队协作范围，已归档为 V2 / V3 输入。
>
> 但它用 9 个真实场景独立验证了我们的定位——**Work Context OS（工作上下文管理）**，
> 并且暴露了 3 个值得补的小洞：
>
> ```Plain Text
> ① 「继续上次」入口
>    回到上次正在处理的事项 / 项目
>    （他们叫"一键恢复工作现场"，我们确实没有）
>
> ② Item 卡片显示"还剩 N 步"
>    读 description 里的 Markdown checklist
>    不加字段、不做子任务
>
> ③ 记录占位文案引导写"为什么"
>    从"今天做了什么？"改成"做了什么 / 为什么这么决定？"
> ```
>
> 3 处都不动模型，成本极低，且直接服务"上下文恢复"这个核心目标。

> **修订说明（V1\.3\.4 可用性补强）**
>
> 本轮来自"真实用户 1 天压力测试"（28 场景 × 3 角色）的结论。
>
> 走查结果：
>
> ```Plain Text
> 判断次数累计：PM ≈ 47 次/天，研发 ≈ 38 次/天，测试 ≈ 40 次/天
> 其中 60% 集中在两处：Inbox 整理 + 早上做计划
> 6 个高危场景里，4 个不是"设计问题"，而是"能力边界"
> ```
>
> 因此本轮补的不是规则，而是**能力边界上的几个洞**：
>
> ```Plain Text
> ① Quick Capture 本地暂存
>    断网时先写本地，联网自动提交
>    （不做完整离线同步，只做"捕获队列"）
>
> ② 手机端只读 + 速记
>    不是做移动端 App
>    只让手机浏览器能"看一眼 Today + 记一句"
>
> ③ Inbox 增加"先收下"入口
>    把一批未整理项一次标成待办（不指定项目），之后再细化
>    解决"30 条要 15 分钟"的问题
>
> ④ Item 卡片显示"最近一条记录"
>    不加字段，只改展示位置
>    解决"被打断后不知道做到哪了"
>
> ⑤ Daily 页面增加"本周"切换
>    不是周报，只是把本周每天的完成事项聚合出来
>
> ⑥ 明确"删除 = 取消"
>    已整理过的事项不物理删除，界面文案要写清楚
> ```
>
> 这一轮之后，产品侧建议**冻结进入原型与实现**。

> **修订说明（V1\.3\.3 交互减负）**
>
> 本轮不改领域模型，只解决一件事：**用户每天需要做多少次判断。**
>
> 起因是第四轮外部走查的结论：
>
> > 模型越来越干净，但用户操作路径仍然偏复杂。
> > WorkOS 的失败方式不会是"数据库设计错了"，
> > 而更可能是"我每天要整理、安排、设置、更新、复盘太多东西，太累了"。
>
> 本轮落地的 15 处：
>
> ```Plain Text
> P0 决策负担
>   ① 「待安排」改成"决策队列"：每条直接给动作
>      [今天做] [排到明天] [暂不安排]
>      暂不安排 = 显式降为 P2，不隐藏
>   ② Today 三层分组微调
>      今天做什么 / 今天别忘了 / 我在等谁 + 还没安排
>   ③ Reminder 三个动作：现在跟进 / 稍后提醒 / 忽略这次
>      忽略提醒不等于处理了业务
>   ④ 明确 Inbox ≠ 待安排（两种不同的心理状态）
>
> P1 维护成本
>   ⑤ WorkLog 定义并改名为"补充事实"（界面文案：记一句）
>   ⑥ "现在跟进"改成三选一快捷操作
>   ⑦ Daily 改成"新增事实 + 更新草稿"，不是重新生成整篇
>   ⑧ 删除 related_company；"人"合并成一个自由文本字段
>   ⑨ 删除 work_log.source（MVP 没有 import）
>   ⑩ 删除 WebSocket；MVP 不做后端 Reminder 调度
>   ⑪ 首次使用：示例数据与真实工作区分离
>   ⑫ 时区按系统/浏览器初始化，不写死 Asia/Shanghai
>
> 补全
>   ⑬ 新增「用户维护成本预算」章节
>   ⑭ 新增原则十一：显式优先于推断
>   ⑮ K3 改为可用性测试；四句"真源关系"写进 PRD
> ```
>
> 模型层只做减法（删 2 个字段），其余全是交互与默认值。

# 产品概述

## 1\.1 产品定位

WorkOS 是一款面向项目型团队成员的**个人工作上下文管理与事项追踪工具**。

它不以传统 Todo List 为核心，而是围绕：

> **我现在有哪些事情、哪些事情最重要、哪些事情正在等待别人、哪些事情需要跟进、我当前项目做到哪里、今天做了什么。**
> 
> 

帮助用户降低多项目、多角色、多事项带来的上下文切换成本。

---

## 1\.2 产品核心价值

WorkOS 解决的核心问题不是“没有地方记 Todo”，而是：

> **工作信息分散、事项数量多、上下文切换频繁、跟进事项容易遗忘、历史工作难以回溯。**
> 
> 

核心价值：

1. 快速记录任何突然出现的事项。

2. 将事项按照项目、状态、优先级、日期进行组织。

3. 区分“我要做”和“我在等别人”。

4. 对需要持续跟进的事情进行提醒。

5. 保存项目当前上下文，降低项目切换成本。

6. 自动沉淀工作记录。

7. 通过 Markdown 日报形成长期工作档案。

8. 支持快速搜索历史工作。

# 产品目标

## 2\.1 MVP 产品目标

MVP 阶段只解决一个核心问题：

> **让用户能够随时记录工作事项，并始终知道当前最重要的事情、正在等待什么、需要跟进什么以及下一步做什么。**
> 
> 

---

## 2\.2 核心指标

MVP 只看一件事：

> **用户是否愿意每天打开它，并且用完之后觉得省力。**

因此指标分两层（V1\.3 收敛）：

```Plain Text
核心指标（4 个）   进 PRD，作为成功标准
观察指标（内部）   只用于验证设计假设，不对外、不作为目标
```

### K1：捕获延迟（Capture Latency）

```Plain Text
定义
  按下快捷键 → 服务端返回保存成功

口径
  P50 ≤ 2 秒
  P95 ≤ 5 秒

不包含
  渲染时间、网络重试时间
```

为什么用 P50 / P95：

> "≤ 5 秒"无法验收，也无法定位问题。
> 分位数能同时反映"通常有多快"和"最差有多糟"。

---

### K2：漏跟率（Follow-up Overdue Rate）

```Plain Text
定义
  已到期 Follow-up 中，超过 24 小时仍未处理的比例

分母
  到达 next_follow_up_at 的 Follow-up 数量
  （不是全部事项）

目标
  周环比下降
```

为什么分母是"到期的 Follow-up"而不是"所有事项"：

> 只有"我答应要推动"的事情才有"漏跟"这个概念。

---

### K3：上下文恢复时间（Context Recovery Time）

```Plain Text
它是可用性测试指标，不是埋点指标（V1.3.3 明确）

不看日志、不做自动统计

执行方式
  1. 选 5~10 个真实项目
  2. 让用户离开这些项目至少 24 小时
  3. 重新打开，要求回答五个问题：
       当前重点是什么？
       当前阻塞是什么？
       下一步做什么？
       最近一次工作是什么？
       现在在等谁？
  4. 记录：完成时间 + 答对率

通过标准
  全部答完 ≤ 10 秒，且五问基本答对
```

为什么不做成"打开页面用了几秒"：

> 页面加载快 ≠ 用户恢复得快。
> 真正的验收标准是"他能不能答出那五个问题"。
>
> 也正因为它是测试指标，所以它不进埋点系统，
> 而是在 MVP 验收阶段人工跑一遍。

---

### K4：日报准备时间（Daily Preparation Time）

```Plain Text
定义
  点击"生成" → 最终保存

口径
  只统计"单次会话内完成保存"的样本
  排除中途离开（否则数据失真）

目标
  中位数 ≤ 3 分钟
```

---

## 2\.3 观察指标（不进 PRD 目标）

这一组只回答一个问题：

> **我们的设计假设是否成立？**

```Plain Text
计划使用率
  有多少工作日真正用了 planned_date
  如果没人用，说明"今日计划"这个设计没有成立

兑现结构
  计划事项最终去向：完成 / 结转 / 改期 / 转 Waiting / 取消
  重点看"无理由反复结转"

Inbox 老化
  Inbox 最老条目天数、平均待整理时长

承诺到期数
  今日到期的、带具体人的跟进数量
  （注意：系统不判断"是不是承诺"，
    只看"有没有人、到没到时间"）
```

规则：

```Plain Text
观察指标不作为目标，不对外公布

否则会重演"完成率 60%"的错误激励：
  计划使用率 → 用户给事情乱填 planned_date
  Quick Capture 次数 → 用户大量捕获但从不整理
```

原则：

> 指标会改变人的行为。
> 凡是能通过"假装做"来达成的指标，都不能当目标。

# 核心工作模型

WorkOS MVP 使用以下核心对象：

```Plain Text
Project
    │
    ├── Context           稳定信息 + 动态状态
    │
    ├── Item
    │     ├── Task        我要做的事
    │     └── Note        只记录，不进入执行流
    │
    │   Item 的能力与状态：
    │     状态     INBOX / TODO / DOING / WAITING / DONE / CANCELLED
    │     能力     计划 / 截止 / 跟进 / 提醒
    │     （Waiting 是状态，Follow-up 是能力，都不是类型）
    │
    ├── WorkLog           人的工作记录
    ├── Activity          系统事件
    │
    ├── Daily
    └── Reminder
```

# 核心概念定义

## 5\.1 Project

项目是用户工作的主要上下文容器。

例如：

```Plain Text
项管系统
用户中心
开放平台
API治理平台
```

项目不是简单的文件夹。

项目应该包含：

- 当前重点

- 当前状态

- 当前阻塞

- 下一步

- 相关事项

- 工作记录

---

# 5\.2 Item

Item 是 WorkOS 中最基本的工作事项。

所有进入系统的事情首先都可以成为 Item。

例如：

```Plain Text
完成工单分配
跟进厂商
等待产品确认
和 PMO 同步
记录技术问题
```

Item 类型：

```Plain Text
Task        我要做的事（默认）
Note        只记录，不进入执行流
```

说明：

> Waiting 是状态，不是类型；Reminder 是独立提醒对象，不是类型。
> Follow-up 也不再是类型，而是 Task 的一种能力（见 5\.4）。
>
> **状态定义生命周期；类型定义业务语义与可用能力。**

能力矩阵（V1\.3）：

| 类型 | 可 WAITING | 可 DONE | 进 Today | 可挂 Reminder | 进日报 |
|---|---|---|---|---|---|
| Task | 是 | 是 | 是 | 是 | 是 |
| Note | 否 | 是（等于归档） | 否 | 否 | 否 |

说明：

> 类型不定义生命周期，但定义"这件事能用哪些能力"。
> 例如 Note 不参与等待流程，也不出现在 Today。

Note 的界面文案（V1\.3\.2）：

```Plain Text
底层复用 status = DONE
但界面上不写"完成"，写"归档"

用户看到：
  记录 → 已归档
而不是：
  记录 → 已完成（用户会问"为什么我的笔记完成了？"）

原则：
  数据模型可以复用，用户概念不能混乱
```

为什么把 Follow-up 从类型降为能力（V1\.3）：

```Plain Text
用户视角
  用户记事时不会想"这是 Task 还是 Follow-up"
  他只会想"我得催一下张三"
  要求他先选类型 = 多一道判断成本，而且选错了没人纠正

模型视角
  "我在跟进什么" 可以由 next_follow_up_at 非空 100% 推导
  不需要一个必须手工维护的标签
  而且时间字段比类型更可靠：用户可能忘选类型，但不会忘设跟进时间

结论
  Follow-up = 能力（next_follow_up_at 非空）
  类型只保留 Task / Note
```

---

# 5\.3 Task

Task 表示：

> **我需要做的事情。**
> 
> 

例如：

```Plain Text
完成工单接口
修复测试 Bug
编写技术方案
```

---

# 5\.4 Follow\-up

Follow\-up **不是 Item 类型，而是 Task 的一种能力**（V1\.3）。

它表示：

> **这件事情当前可能不需要我立即做，但未来需要我主动关注。**
> 
> 

例如：

```Plain Text
跟进厂商问题
跟进研发接口
跟进测试结果
跟进产品需求
```

模型定义：

```Plain Text
Follow-up = next_follow_up_at 非空
```

也就是：

```Plain Text
Task（type）
  + next_follow_up_at = 2026-09-25 10:00
        ↓
它就是一条"跟进事项"
  出现在"待跟进"分区与 Follow-ups 工作台
```

这意味着：

```Plain Text
不再需要用户手动选"跟进"类型
不会再出现"这条是 Task 还是 Follow-up"的纠结
不会因为用户忘选类型而漏掉了一条跟进
```

它与 Waiting 的关系：

```Plain Text
Waiting      status = WAITING          现在在等别人
Follow-up    next_follow_up_at 非空     我下一次主动推动的时间

两者可以同时成立：
  status = WAITING
  waiting_for = 厂商A
  next_follow_up_at = 9/25 10:00
```

为什么这个区分重要（V1\.3）：

> "等待"和"跟进"是两个正交维度，
> 一件事可以同时"在等别人"和"我答应了要主动催"。
> 把它们做成两个类型，会强迫用户二选一。

## 跟进动作（V1\.3\.1 定义，V1\.3\.3 改为快捷操作）

背景：

```Plain Text
用户点"现在跟进"之后，真实动作可能是：
  打了个电话 / 发了微信 / 发了邮件 / 当面问了一句

如果系统这时要求"填写一条工作记录"，
用户的第一反应是：太麻烦，先不点。
```

所以"现在跟进"必须是一个**三选一的快捷操作**，不是打开编辑页：

```Plain Text
┌──────────────────────────────────────────┐
│ 厂商接口问题                              │
│                                          │
│ 结果？                                    │
│                                          │
│ [ 对方没回 ]   [ 对方给了 ]   [ 暂时不跟 ] │
└──────────────────────────────────────────┘
```

三种结果的行为：

```Plain Text
对方没回
  记一条工作记录（系统先生成默认文案："已跟进 XX"）
  → 下次跟进？[明天] [2 天后] [自定义]
  status 保持 WAITING

对方给了
  → status WAITING → DOING（继续做）或 DONE（到此为止）
  → 清空 waiting_*
  → 可选：补一句

暂时不跟
  → next_follow_up_at = null
  → 它从"待跟进"消失，但仍留在 Items
```

设计要点：

> 用户真正需要的是"**处理掉这个提醒**"，
> 而不是"填写一条工作日志"。
> 系统可以在背后替他留下记录（默认文案），他不需要打字。

不许出现"点完什么都不发生"。

---

# 5\.5 Waiting

Waiting 表示：

> **事情当前卡在别人或外部条件，我需要等待。**
> 
> 

例如：

```Plain Text
等待厂商提供解决方案
等待产品确认需求
等待研发完成接口
等待测试结果
```

Waiting 是 WorkOS MVP 的核心能力之一。

注意：

> Waiting 在数据模型中是 **Item 的状态（status = WAITING）**，不是 Item 类型。
> 进入 Waiting 必须填写"等待谁"（waiting_for）。

Waiting 的四个对象/时间（V1\.2 补齐）：

```Plain Text
waiting_for          在等谁
waiting_since        什么时候开始等
waiting_expected_at  对方预计什么时候给结果（可空）
next_follow_up_at    如果对方没给，我什么时候主动跟
```

有了 waiting_since，系统才能回答：

> "这件事已经等了 3 天。"

有了 waiting_expected_at，系统才能回答：

> "对方已经逾期 2 天还没给。"

退出 Waiting 时的字段处理（V1\.3\.1 补齐）：

```Plain Text
status 从 WAITING 变为 TODO / DOING / DONE 时

  清空 waiting_for
  清空 waiting_since
  清空 waiting_expected_at

  同时写一条 Activity 保留历史：
    type   = WAITING_ENDED
    remark = "已等待 3 天"
```

不能只是"保留旧值"：

```Plain Text
保留会导致下次进入 WAITING 时 waiting_since 是旧的，
系统会算出"已等待 12 天"这种错误数字
```

不能只是"清空、什么也不留"：

```Plain Text
那样会丢掉"上次等了多久"这个事实，
而它恰恰是复盘"为什么这个项目慢"的关键证据
```

进入 Waiting 时的轻提示（V1\.3\.1）：

```Plain Text
"要不要写一句现在做到哪了？"

因为模型里没有"Item 进度"字段，
"做到一半"的事实只能靠 WorkLog 留下
```

---

# 5\.6 Work Log

Work Log 是用户在工作过程中产生的实际工作记录。

例如：

```Plain Text
09:30 完成工单数据模型
10:20 与产品确认需求
14:00 完成接口开发
16:30 发现厂商接口问题
```

Work Log 是日报和项目历史的基础数据。

**Work Log ≠ 系统事件（V1\.2 明确）**

两者是两类不同的东西：

```Plain Text
WorkLog
    人记录：我实际做了什么

Activity
    系统记录：这条事项发生了什么变化
```

例子：

```Plain Text
Activity
14:20  事项状态 TODO → DOING

WorkLog
14:35  与产品确认客户范围规则
```

规则：

> 系统事件用于历史与审计，**默认不能进入日报的"工作内容"**。
> 日报的内容来源是人工 WorkLog 与已完成事项。

Work Log 的准确定义（V1\.3\.3）

背景：

```Plain Text
V1.3.2 已经把 WorkLog 降为"可选"
  但它在产品里仍然被赋予很多价值：
    日报、项目历史、跟进历史、上下文
        ↓
  用户会形成一个隐性认知："是不是还是应该写？"
        ↓
  WorkLog 又变回了隐形强制项
```

所以把定义再收紧一句：

> **只有 Item 表达不了的事实，才值得写 Work Log。**

| 情况 | 要不要写 |
|---|---|
| 完成工单接口 | **不用写** —— `Item = DONE` 已经说明 |
| 与产品确认：客户范围按组织维度过滤 | **值得写** —— Item 表达不了这个过程 |
| 厂商说接口文档明天下午提供 | **值得写** —— 这是沟通事实 |
| 发现原方案有性能问题，准备改批量查询 | **值得写** —— 这是上下文 |

界面文案（V1\.3\.3）：

```Plain Text
❌ 工作记录        （听起来像义务）
✅ 记一句          （听起来像顺手）
```

按钮位置：Item Drawer 里，完成事项之后**不弹窗**，只在需要时点。

占位文案要引导写"为什么"（V1\.3\.5）

背景（来自"产品经理的一天"场景）：

```Plain Text
两天后研发问："这个为什么这样设计？"
        ↓
产品经理："……"（忘了）
        ↓
他们的解法是"需求决策链"（自动关联会议/讨论/变更）
        ↓
那需要跨系统集成，MVP 不做
        ↓
但我们有一个零成本的办法：改占位文案
```

改动：

```Plain Text
❌ 占位："今天做了什么？"
✅ 占位："做了什么 / 为什么这么决定？"
```

为什么值得：

```Plain Text
用户最容易漏记的，恰恰是"当时为什么这么定"
  而它正是三天后最容易被追问的东西

改一个字符串，就能显著提高"理由"被写下来的概率
比新增一个"决策链"字段便宜得多，也真实得多
```

# 5\.7 Daily

Daily 是指定日期的工作日报。

日报本质上是：

> **某一天工作内容的 Markdown 文档。**
> 
> 

它可以引用：

- Task

- Follow\-up

- Work Log

- Waiting

- 项目

---

# 5\.8 Context

Context 是项目的当前工作状态。

核心字段：

```Plain Text
当前目标
当前重点
当前进展
当前阻塞
下一步
```

Context 的目的：

> **让用户离开项目几小时甚至几天后，重新进入项目时，可以快速恢复工作状态。**
> 
> 

Context 是**结构化状态板，不是 Markdown 文档**（V1\.2 明确）：

```Plain Text
稳定信息（几乎不变）
  goal          当前目标
  key_people    关键人员
  key_links     关键链接

动态状态（会变，但不要求每天改）
  focus         当前重点
  blocker       当前阻塞
  next_action   下一步
  progress_note 当前进展（一句话）

Markdown（可选补充）
  notes_markdown
```

为什么要把 Context 拆成两组（V1\.3）：

```Plain Text
稳定信息
  用户半年才会改一次
  不需要提醒维护

动态状态
  会随项目推进变化
  需要保鲜提示

不拆开的后果
  用户被要求维护 7 个字段
  3 个月后一定会说"又让我更新 Context？"
```

关于 `progress_note`（原 current_progress）：

```Plain Text
它回答的是核心五问之一：
  "我这个项目上次做到哪里？"

因此不能删除。

但必须明确它的语义：
  它是我对现状的一句主观判断
  不是系统计算出来的进度百分比

错误理解：
  progress = 80%
正确理解：
  progress_note = 接口已完成，等联调
```

V1\.3\.2 减负调整：把它降为**可选字段**，并由系统给出默认文本。

```Plain Text
当前进展（可选）

默认建议（系统生成，用户可改可删）：
  最近完成：完成工单接口
  正在进行：工单联调

用户只改两个字就能存，不改也能存
```

为什么这样改：

```Plain Text
① 强制手写"当前进展"是重复劳动
   系统已经知道"最近完成了什么、正在做什么"

② 但删除这个字段也不行
   一个"最近没有完成任何事项"的项目
   就再也答不出"我上次做到哪了"

③ 所以：保留字段 + 系统给默认值 + 允许为空
   这对应原则十（用户只记录事实一次）
```

规则：

> Today、项目卡片、项目切换都需要在 10 秒内读取"当前重点 / 阻塞 / 下一步"。
> 如果这些字段是 Markdown，前端又要重新解析，得不偿失。
> 需要长文时，写进 `notes_markdown`。

# 功能背景与意义

这一章回答的是："每个功能为什么存在、解决什么、不做什么"。

产品调研阶段用来判断"该不该做"；研发阶段用来避免"做着做着变味"。

读法：

```Plain Text
背景 = 用户真实遇到的问题
意义 = 它在 WorkOS 的闭环里承担什么角色
边界 = 明确不做成什么，防止功能膨胀
```

加上第四行（V1\.3\.1）：

```Plain Text
用户语言 = 素人听得懂的一句话
```

每一节都必须有"用户语言"这一行，否则过不了素人测试（见原则八）。

## 6\.0 术语 → 用户语言对照表（V1\.3\.1）

我们的术语**不应该出现在界面上**。界面文案以下表为准。

| 我们的术语 | 界面 / 用户看到的说法 |
|---|---|
| Item | 这件事（界面上不出现 Item） |
| Item Type | 类型：任务 / 记录 |
| Project Context | 项目现状 |
| planned_date | 今天做 / 排到哪天 |
| due_at | 截止 |
| next_follow_up_at | 跟进时间 |
| waiting_for / waiting_expected_at | 等谁 / 对方说什么时候给 |
| Inbox | 待整理 |
| Today | 今天 |
| 待安排 | 还没安排 |
| Daily / 收工复盘 | 今天收个尾 |
| WorkLog | 工作记录 |
| Activity | 活动（默认折叠，用户不需要主动理解） |
| Waiting | 等别人 |
| Follow-up | 该催谁了 / 我答应谁什么时候回话 |
| Reminder | 提醒 |
| Items | 所有记录（用来"找以前记过的东西"） |

规则：

```Plain Text
界面文案以本表为准
新增功能时，必须同时补一行"用户语言"
```

## 6\.1 快速捕获（Quick Capture）

```Plain Text
背景
  工作被打断时，想法只存在几秒
  打开系统、选项目、填字段，想法就没了

意义
  把"记录"的成本压到最低，让捕获不再需要先决策
  它是整条闭环的入口：没有捕获，后面全是空的

边界
  只要求标题，不要求项目 / 日期 / 优先级
  不做 AI 解析（V1）
  失败时保留输入，绝不因为网络问题清空用户刚写的内容
  断网时先写本地，联网自动提交（V1.3.4）

用户语言
  想到什么就先记一句，别管格式
```

本地暂存（V1\.3\.4 新增）

背景（来自场景 27）：

```Plain Text
"5 秒记一句"是这个产品的入口 KPI
        ↓
但断网时它直接失败
        ↓
虽然界面保留了输入 + 重试按钮，
但那要求用户"回到现场手动重试"
        ↓
他的想法已经没了
```

做法：

```Plain Text
输入
 ↓
先写入本地队列（IndexedDB / localStorage）
 ↓
尝试提交
 ├── 成功 → 从队列删除，提示"已记录"
 └── 失败 / 离线 → 留在队列，界面立刻显示"已记录（待同步）"
                    ↓
              联网后自动提交
              提交成功 → 从队列移除
```

三条约束：

```Plain Text
① 这不是"离线编辑"
   只暂存"新捕获的条目"，不涉及修改已有数据
   所以不需要冲突解决、版本合并、离线 ID

② 必须防重复提交
   前端提交时禁用 + 成功后从队列移除

③ 用户必须看得见状态
   队列里有几条、是否已同步，都要显示
```

与"MVP 不做离线"的关系（重要）：

```Plain Text
我们不做：离线编辑、双向同步、冲突合并
我们做：  捕获队列（只写不读、只新增不改）

因为捕获是入口，
入口断一次，用户就不信这个工具了。
```

## 6\.2 Inbox（待整理）

```Plain Text
背景
  捕获进来的东西一定是杂乱的
  如果不区分"已整理 / 未整理"，系统很快会被垃圾淹没

意义
  提供一个"先记下、后处理"的缓冲区
  让捕获与整理分成两个动作

边界
  Inbox 是处理队列，不是长期列表
  必须有治理机制（数量与最老条目提示），否则它自己会变成垃圾场

用户语言
  先扔进去，回头再收拾
```

## 6\.3 Item（事项）与类型 / 状态

```Plain Text
背景
  用户的工作里既有"我要做的事"，也有"只记一下"的信息
  但用户不会在记录时先做分类

意义
  Item 是唯一的执行单元
  状态描述生命周期，类型描述可用能力

边界
  只有两种类型：Task / Note
  Waiting 是状态，Follow-up 是能力，Reminder 是独立对象
  不引入子任务（不建 parent_id）
  Note 的界面文案是"记录 → 已归档"，不是"完成"

用户语言
  一件事就是一件事，不用先分类
```

## 6\.4 今日计划（Plan）

```Plain Text
背景
  待办一多，用户打开首页先看到一堆事
  系统替他把所有重要的都列出来，反而更难开始

意义
  让用户显式选择"今天做哪几件"
  把 Today 从"过滤器"变成"决策面"

边界
  建议 3 件；超过 3 件只轻提示，不设硬上限（V1.3.2 修正）
  不做自动结转（未完成必须由用户显式取舍）
  planned_date 只表示"我打算今天做"，不等于截止时间

用户语言
  今天我就做这三件
```

关于容量（V1\.3\.2 修正）：

```Plain Text
旧版：软上限 3 件 + 硬上限 5 件

问题
  "3" 和 "5" 是设计者的偏好，不是用户的事实
  对开发：上午修线上问题、下午开发、晚上联调，
          再加产品确认和 Code Review，一天不止 5 件
  对 PM：今天要跟 8 个事项也可能合理

新版
  默认建议 3 件
  超过 3 件 → 轻提示："今天已经安排 4 件了，确定继续吗？"
  不设硬上限，但持续提醒：
    "Today 是今天真正准备处理的事，不是所有待办"
```

## 6\.5 Today 六个分区

```Plain Text
背景
  "我现在最该做什么"是每天第一个问题
  但优先级列表无法回答它

意义
  用固定的六个分区回答今天要看什么
  每个分区都能一句话解释"为什么在这"

边界
  统计层互斥（数字可相加），展示层允许次级标签
  不做权重打分、不做推荐引擎
  ⑥ 是"待安排"（捕漏），不是"建议"（替用户规划）

用户语言
  打开就知道今天该看什么
```

## 6\.6 早晨简报

## 6\.7 Waiting（等待）

```Plain Text
背景
  很多工作不是卡在自己身上，而是卡在别人身上
  这类事情在传统待办里最容易被遗忘

意义
  把"在等别人"变成一等状态，而不是待办里的一条普通事项
  回答"我现在在等谁、等了多久、对方该不该给了"

边界
  waiting_for 必填，waiting_since 自动记录
  waiting_expected_at 只做标记，不改变分区归属
  Waiting 不等于"这条事项不能做别的事"（一个 Item 一个闭环事项）

用户语言
  这件事不在我手上，我在等别人
```

## 6\.8 Follow-up（跟进能力）

```Plain Text
背景
  等待不会自己结束，必须在某个时间主动推动
  但"我要主动催一下"这件事很容易忘

意义
  用 next_follow_up_at 表达"我答应要推动"
  支撑"不漏跟"这个核心承诺

边界
  不是 Item 类型，而是 Task 的能力
  不是状态：它和 WAITING 可以同时成立
  提醒文案要带上具体的人，但不能替用户断言承诺（V1.3.2）

用户语言
  我答应谁什么时候回话 / 我该催谁了
```

## 6\.9 WorkLog（工作记录）

```Plain Text
背景
  一天结束后，人记不清自己具体做了什么
  而日报与复盘都需要这些事实

意义
  记录"我实际做了什么"
  它是日报的原料，也是项目历史的最小单位

边界
  只记录人的工作，不记录系统事件

用户语言
```

## 6\.10 Activity（系统事件）

```Plain Text
背景
  如果系统把"状态变化"写进工作记录，日报就会变成流水账

意义
  给系统事件一个独立位置：历史回溯、审计、上下文保鲜判断

边界
  绝不出现在日报的"工作内容"里

用户语言
```

## 6\.11 Daily（日报）与收工复盘

```Plain Text
背景
  日报往往是"下班后再重新整理一遍"，成本高，所以容易不写
  而下一天又要重新回忆昨天做到哪

```

```Plain Text
背景
```

# 默认行为矩阵（Default Behavior Matrix）（V1\.3\.2 新增）

这一章回答研发最关心的一个问题：**什么都不设置时，系统怎么工作？**

产品文档里到处是"可以设置""可以筛选""可以调整"，
但真正决定体验的是默认值。这份表可以直接当研发的验收清单。

| 场景 | 默认行为 |
|---|---|
| 快速记录 | `status = INBOX`、`type = TASK`、`priority = P2`、无项目、无日期 |
| 新建 Task | `priority = P2` |
| 新建 Note | `priority = P2`；不进 Today / 日报 / Reminder；DONE 在界面上叫"已归档" |
| 新建项目 | `status = ACTIVE` |
| 事项没有项目 | 允许；日报里归入"未归属"分组 |
| 事项没有日期 | 不进今日计划；不进 Today 的②③ |
| P0 / P1 且无日期 | 进 ⑥ 待安排 |
| 今日计划容量 | 建议 3 件；超过 3 件轻提示；**无硬上限** |
| 次日未完成的计划 | 不自动结转；进简报"需要你决定" |
| 进入 WAITING | `waiting_for` 必填；`waiting_since` 自动写入 |
| 退出 WAITING | 清空 `waiting_*`；写 Activity(`WAITING_ENDED`) |
| 设置 `next_follow_up_at` | 即具备"跟进"能力，进入跟进视图 |
| 跟进到点 | 出现在 Today ④ 待跟进 |
| `waiting_expected_at` 到期 | 只打"对方逾期"标记，不改变分区归属 |
| Reminder 到期 | 只影响提醒展示，**不改变业务状态** |
| 完成 Task | `completed_at = now`；写 Activity；**不写 WorkLog** |
| 取消事项 | `cancelled_at = now`；可恢复（CANCELLED → TODO） |
| 撤销完成 | `completed_at` 清空；历史记录保留 |
| Daily 生成 | 生成 `generated_content`；**不覆盖** `content` |
| Daily 的"明日计划" | 来自 `planned_date`；在 Markdown 里改**不回写** Item |
| 未完成计划 | 不自动结转，必须由用户显式处理 |
| Project Context | 不自动修改；`progress_note` 可空，为空时用系统建议文本 |
| Inbox | 保留原始记录，不自动分类；顶部提供"整理最老的一条"和"先都收下"（V1\.3\.4） |
| 整理完成条件 | `status != INBOX` 即算整理过（不要求填项目，V1\.3\.4） |
| 未分类计数 | `project` 为空且未完成的数量；显示在简报与 Items 快捷筛选，不催不排序（V1\.3\.5） |
| App 未打开时的提醒 | 打开 App 后一次性补偿展示 |
| 首次使用 | 写入示例数据（`code = DEMO`、相对日期、可清除、埋点排除） |
| 删除 | 默认走"取消"，不物理删除 |
| 时区 | 首次启动读系统 / 浏览器时区（V1\.3\.4），是"今天"的唯一真源 |
| 日界线 | 默认 0 点（自然日）；字段保留但 MVP 不进界面 |
| 搜索 | 关键词 + 轻量前缀（`project:` / `status:` / `person:`） |
| 断网时的捕获 | 先写本地队列，界面显示"待同步"，联网自动提交（V1\.3\.4） |
| Today 顶部 | 显示"你上次在做：…（N 小时前）[继续]"（V1\.3\.5） |
| Item 卡片 | 显示"最近一条记录"与"还剩 N 步"（读描述里的 checklist）（V1\.3\.5） |
| 导出 | Markdown 按项目分目录 + 全量 JSON，人可读 |
| 备份 | 每日一次，写到与数据库**不同的存储位置**，保留 14 份 |

使用规则：

```Plain Text
研发可以直接按本表写默认值
任何"默认行为"的改动，都要回到本表更新
本表与其它章节冲突时，以本表为准
```

# 用户维护成本预算（V1\.3\.3 新增）

WorkOS 真正的竞争对手不是 Notion，而是：

```Plain Text
用户自己的大脑
微信收藏
浏览器标签页
备忘录
Excel
聊天记录
```

用户不会"因为功能少"而弃用，只会因为"每天要维护的东西太多"而弃用。

因此给核心动作定一个成本上限：

| 动作 | 成本上限 |
|---|---|
| 快速记录一条 | ≤ 5 秒（Web 内 ≤ 3 秒） |
| 整理一条 Inbox | ≤ 30 秒 |
| 完成一件事 | **≈ 0 秒额外成本** |
| 进入等待（填等待对象 + 预计时间） | ≤ 10 秒 |
| 设一次跟进时间 | ≤ 5 秒 |
| 记一句补充记录 | ≤ 15 秒 |
| 收工写日报 | ≤ 3 分钟 |

更重要的是一条硬规则：

> **任何核心流程，都不能因为"顺便让用户补个数据"而增加额外步骤。**

反例与正例：

```Plain Text
❌ 完成任务
     完成 → 写工作记录 → 更新 Context → 更新日报 → 确认提醒

✅ 完成任务
     完成 → DONE

   系统自动知道：
     完成了什么 / 属于哪个项目 / 什么时候完成
   其余全部可选
```

怎么用它：

```Plain Text
任何新功能上线前，先估一下它给用户加了多少秒
如果它让某个核心动作超过上限 → 要么改交互，要么砍掉
它和原则十（用户只记录事实一次）是同一件事的两个视角：
  原则十管"要不要让用户做"
  成本预算管"让他做的话要花几秒"
```

# 交互冻结测试清单（V1\.3\.5 新增）

冻结不等于可以直接写代码。

进入原型阶段后，必须先跑这份清单；跑完通过才算"可以进研发"。

## 六个必须验证的点

| # | 验证点 | 通过标准 |
|---|---|---|
| ① | Quick Capture → Inbox → Today 全链路 | 按快捷键到 Inbox 出现 ≤ 5 秒（Web ≤ 3 秒）；全程 **0 次判断** |
| ② | "继续上次"必须直达 | 1 次点击打开 Item，≤ 2 秒；**不允许**走"项目 → 事项 → 记录"三层 |
| ③ | "还剩 N 步"不能长成子任务 | 卡片一行；点击直达描述区；**不出现** SubTask / Assignee / DueDate |
| ④ | "先都收下"要特别测 | 30 条 ≤ 5 秒；明确"收下 ≠ 已经计划"；处理完要有"未分类"计数兜底 |
| ⑤ | Today 不能变"聪明" | 每条都能一句话解释"为什么在这里"；**不出现** AI 排序 / 行为预测 / 自动重要度 |
| ⑥ | Reminder 不能造成错觉 | 忽略提醒不改变 `next_follow_up_at`；界面不出现"已送达 / 已读" |

## 三个容易漏掉的高危场景（来自 28 场景走查）

```Plain Text
⑦ 断网时的捕获
     断网 → 记录 → 界面显示"待同步" → 联网自动提交
     通过标准：想法不丢，用户不需要手动重试

⑧ 手机上看一眼
     375px 宽下能打开 Today（只读）并记录一句
     通过标准：会议室里能查、能记

⑨ 一周后回顾
     Daily 切"本周"能看到本周完成与记录
     通过标准：≤ 90 秒内回答"上周我干了什么"
```

## 判定方式

```Plain Text
定量部分（秒数 / 次数）→ 对照「用户维护成本预算」
定性部分（能不能一句话解释）→ 找 1 名真实用户 + 1 名不熟悉产品的同事各跑一遍

只要出现"用户需要连续做 5 个以上判断"的场景，
就判定为阻断问题，回到设计。
```

## 用什么跑

```Plain Text
可点的原型（不需要真后端）
  Today / Inbox / Item Drawer / 项目现状 / Daily 五个界面
加假数据，覆盖：
  正常工作日 / 高压工作日 / 频繁会议日 / 线上事故日 / 临时需求日 / 加班日
```

# 信息架构

MVP 一级导航（V1\.3 从 7 个收敛为 5 个）：

```Plain Text
WorkOS
│
├── Today        今日决策与执行（含"等待与跟进"区块）
│
├── Inbox        待整理
│
├── Items        全部事项（含"跟进"筛选视图）
│
├── Projects     项目与上下文
│
└── Daily        工作沉淀与复盘

Settings
Search           全局搜索（⌘K，不作为独立导航项）
```

为什么收敛导航（V1\.3）：

```Plain Text
原来的 7 个一级导航：
  Today / Inbox / Items / Follow-ups / Projects / Daily / Calendar

问题
  个人工具里，一级导航越多，用户越容易"什么都找不到"
  用户不需要每天进"等待与跟进"页面
  他只需要在 Today 上看到"谁欠我什么、我欠谁什么"

调整
  Follow-ups 下沉：
    Today 上的"待跟进 / 等待中"区块
    +
    Items 的"跟进"筛选视图

  Calendar 后置到 V1\.1
    它的价值（从时间看事项）已被
    Today + Items 日期筛选 + Daily 覆盖
```

Inbox 与"待安排"的区别（V1\.3\.3 明确）

背景：

```Plain Text
用户快速记一句"跟进厂商接口问题"
        ↓
它进 Inbox
        ↓
整理时设成 P1、无日期
        ↓
它离开 Inbox，出现在 Today 的"待安排"
        ↓
用户的困惑："我明明整理完了，为什么它还在首页？"
```

根因是：Inbox 和待安排**都在表达"还没处理"，但是两种不同的心理状态**。

```Plain Text
Inbox（界面文案：待整理）
  这件事我甚至还没决定怎么处理

待安排（界面文案：还没安排）
  我已经承认这是一件正式的工作，
  但还没决定什么时候做
```

规则：

> 界面上直接使用这两句话作为空状态与说明文案，
> 不要指望用户自己理解"整理"和"安排"的区别。

# Today 今日工作台

## 7\.1 产品目标

Today 是用户打开 WorkOS 后默认进入的首页。

核心目标：

> **告诉用户今天应该关注什么。**
> 
> 

具体到 V1\.3：

```Plain Text
打开 App
        ↓
30 秒内知道：
  今天计划了哪几件
  哪些已经晚了
  哪些今天到期
  哪些在等我跟进
  哪些我在等别人
        ↓
开始工作
```

因此 Today 不是"把所有重要事项列出来"的过滤器，
而是一个**可决策的工作台**：

```Plain Text
① 今日计划（用户显式选择，默认 3 件）
② 逾期
③ 今日到期
④ 待跟进
⑤ 等待中
⑥ 待安排（规则见下，上限 5 条 + 查看全部）
```

在界面上，这 6 个分区归成三块（V1\.3\.2）：

```Plain Text
今天做什么
  ① 今日计划

今天别忘了
  ② 逾期
  ③ 今日到期
  ④ 待跟进

我在等谁 / 还没安排
  ⑤ 等待中
  ⑥ 待安排
```

为什么改（V1\.3\.2 起，V1\.3\.3 微调）：

```Plain Text
6 个同级列表 → 用户仍然会问"我到底先做哪个？"
3 块 → 回答三个决策问题：
  今天做什么？        （我自己定的）
  今天别忘了什么？    （有时间压力的）
  我在等谁 / 还没安排？（挂在别人那，或压在手里的）

为什么"等待中"不放进第二块（与外部建议不同）
  "我在等谁"是 WorkOS 相对普通待办的头号差异点
  我们的用户（PM / 产品）每天都要看："在等谁、等了几天、对方该不该给了"
  把它和"还没安排"混在一起，会削弱核心价值
  所以第三块叫"我在等谁 / 还没安排"，等待在前

注意
  分区规则不变，只是分组展示
  6 个分区的去重与计数规则继续有效
```

⑥ 的定位（V1\.3 关键修正）：

```Plain Text
它不是"推荐"（系统替我决定做什么）
也不是"过滤"（把所有重要的都列出来）

它是"捕漏"：
  把我忘了安排、但其实重要的事捞回来

所以 UI 文案是：
  "这条还没安排，要不要放到今天？"
而不是：
  "建议你处理这条"
```

原则：

> **Today 必须是可解释的，不能是神秘的。**
> 一条事项出现在 Today，用户必须能一句话说出为什么。

归属与展示规则（V1\.2 分层）：

```Plain Text
统计层：一条事项只归属一个主分区
        → 简报数字可直接相加，不相交

展示层：允许叠加"次级状态标签"（最多 2 个）
        → 不改变主分区归属，只补充上下文
```

允许的次级标签（固定集合，不新增）：

```Plain Text
今日计划
逾期 N 天
今天到期
跟进 10:00
等待 XX
对方逾期 N 天
```

说明（V1\.3\.1）：

> 补「今天到期」是因为一条事项若已归属 ① 今日计划，
> 用户仍然需要看到"它今天到期"这个信息。
> 标签最多 2 个，按优先级取：
>   等待 XX > 跟进 > 对方逾期 > 逾期 > 今天到期 > 今日计划

例子：

```Plain Text
① 今日计划

☐ P0 跟进厂商接口
   等待 XX厂商 · 跟进 10:00
```

理由：

> "在等谁"和"什么时候该跟进"是 WorkOS 最关键的上下文，
> 不能因为这条事项已经归属"今日计划"就被隐藏。

Item 卡片上还要显示"最近一条记录"（V1\.3\.4）

背景（来自场景 11）：

```Plain Text
用户做到一半被叫走，两小时后回来
        ↓
他最想知道的是"我刚才做到哪了"
        ↓
但 Item 没有"进度"字段
  只能靠 description、或翻 Activity / 记录
        ↓
结果：要么现场回忆，要么放弃这条、去做别的
```

做法（不改模型，只改展示位置）：

```Plain Text
┌────────────────────────────────────────┐
│ □ 完成工单分配接口                      │
│ P1 · 项管系统 · 今天 18:00              │
│ 最近：接口已写完，等联调    09-22 14:30  │
└────────────────────────────────────────┘
```

数据来源：

```Plain Text
该事项最近一条工作记录（WorkLog）
没有记录时 → 显示最近一条 Activity 的摘要
                  （例如"状态 TODO → DOING"）
都没有时   → 这一行不显示
```

为什么有效：

> "我做到哪了"这个问题，
> 80% 的场合看一眼卡片就够了，
> 不需要打开 Drawer、也不需要系统新增进度字段。

卡片上再补一行"还剩 N 步"（V1\.3\.5）

背景（来自"研发的一天"场景）：

```Plain Text
研发上午写支付接口，下午回来："我写到哪了？"
        ↓
他们的解法是"工作恢复卡片：做到 80%，待做 1/2/3"
        ↓
但"80%"我们明确拒绝（progress_note 都不是百分比）
        ↓
而"待做 1/2/3"我们其实有地方放：
  description 支持 Markdown checklist
```

做法：

```Plain Text
┌─────────────────────────────────────────┐
│ □ 完成工单分配接口                       │
│ P1 · 项管系统 · 今天 18:00               │
│ 最近：接口已写完，等联调                  │
│ 还剩 3 步（来自描述里的清单）             │
└─────────────────────────────────────────┘
```

规则：

```Plain Text
统计 description 里未勾选的 checklist 项数量
  > 0 → 显示"还剩 N 步"
  = 0 或没有 checklist → 不显示这一行

只在卡片上显示，不给它单独字段、不做子任务
点击这一行 → 打开 Drawer 的描述区
```

用户语言：

> 这条我还剩几步没做完

为什么不做成"进度百分比"：

```Plain Text
百分比是主观的、要维护的
checklist 是客观的、已经写好的
前者增加成本，后者零成本复用
```

## 7\.3 Today 顶部的「继续上次」（V1\.3\.5 新增）

背景（来自"临时插入"场景）：

```Plain Text
真实工作不是 A→B→C，而是：
  A → BUG → 会议 → 需求 → 客户 → 回 A
        ↓
回来时用户要的不是"给我数据"，
而是"把我放回刚才那个工作现场"
        ↓
我们有 Today、有 Context、有卡片上的最近记录，
但缺一个"直接回到刚才那条事项"的入口
```

设计：

```Plain Text
Today 顶部（首次打开时，在"需要你决定"下方）

┌──────────────────────────────────────────────┐
│ 🕘 你上次在做：完成工单分配接口（2 小时前）    │
│                                    [继续]     │
└──────────────────────────────────────────────┘
```

规则：

```Plain Text
记录    最近一次打开过的 item_id / project_id
        存在本地（不上服务端），避免多设备歧义

显示条件
  与上次打开间隔 ≥ 30 分钟（太近没有意义）
  且该事项未完成

点击"继续"
  打开该事项的 Drawer（停在描述区）
  如果是项目级操作，则打开该项目页

不显示
  最近没有打开过任何事项
  该事项已完成 / 已取消
```

为什么存在本地：

```Plain Text
它只是"我刚刚在看什么"，是一个会话状态，
不是业务事实
放服务端会引出"多设备以哪个为准"的问题，
而这个问题在 MVP 里不值得回答
```

用户语言：

> 我刚才在做什么，点一下就回去

提醒的三个动作（V1\.3\.3）

背景：

```Plain Text
10:00 提醒："该催张三了：接口方案"

用户点"关闭提醒"
        ↓
这并不代表"我已经催了张三"
        ↓
可能只是"我现在不想看这个提醒"

如果把"关闭提醒"当成"已处理"，业务事实就丢了
```

所以提醒条上给三个动作，且与业务动作严格分离：

```Plain Text
┌──────────────────────────────────────────┐
│ 🔔 该催张三了：接口方案                    │
│                                          │
│ [现在跟进]  [稍后提醒]  [忽略这次]         │
└──────────────────────────────────────────┘
```

| 动作 | 对 Reminder | 对业务事实（Item） |
|---|---|---|
| 现在跟进 | Reminder → 已处理 | 记一条工作记录；更新下次跟进时间或改状态 |
| 稍后提醒 | 修改 `remind_at` | **不变** |
| 忽略这次 | Reminder → 已处理 | **不变**（`next_follow_up_at` 保持原值） |

"稍后提醒"的默认档位（V1\.3\.5）：

```Plain Text
[ +1 小时 ]  [ 今天 18:00 ]  [ 明早 9:00 ]  [ 自定义 ]

默认选中 [+1 小时]
不用让用户先去想"稍后是多久"
```

原则：

> **提醒是注意力机制，不是业务状态。**
> 关掉提醒 ≠ 处理了事情。

⑥ 待安排的候选规则（V1\.3 简化）：

```Plain Text
未计划 + 未完成 + 非 WAITING
AND priority IN (P0, P1)

上限 5 条

排序
  priority ASC
  → due_at ASC NULLS LAST
  → updated_at DESC
```

它不是一个列表，而是一个"决策队列"（V1\.3\.3）

背景：

```Plain Text
假设用户有 6 条 P1，全部未安排
        ↓
待安排 = 6
        ↓
用户看到："还有 6 件重要事情没安排"
        ↓
下一秒还是不知道："那我今天到底做哪一个？"

原因
  一个"又一份重要事项列表"，
  只把焦虑从 Today 转移到了"待安排"，
  没有帮用户完成决策
```

因此每条待安排事项都直接给动作：

```Plain Text
┌──────────────────────────────────────┐
│ P1 跟进厂商接口                       │
│ 为什么在这：P1 · 未安排               │
│                                      │
│ [今天做]  [排到明天]  [暂不安排]      │
└──────────────────────────────────────┘
```

三个动作的语义：

```Plain Text
今天做
  → planned_date = 今天，进入 ① 今日计划

排到明天
  → planned_date = 明天
  → 今天不再出现在待安排

暂不安排
  → priority 显式降为 P2
  → 今天不再出现在待安排
```

为什么"暂不安排"是降优先级，而不是隐藏 N 天：

```Plain Text
如果做成"隐藏 7 天再冒出来"
  → 又是一条系统推断规则
  → 而且用户会怀疑"我是不是丢了一条"

改成"显式降为 P2"
  → 用户看得见后果（优先级变了）
  → 符合原则十一：显式优先于推断
  → 也不会重新掉回"记录完就找不到"
```

用户语言：

```Plain Text
"这几条我知道重要，但还没定什么时候做"
```

这条规则在 V1\.3\.1 被修正过：

```Plain Text
V1.3（错误）
  未计划 + 未完成 + 非 WAITING
  AND ( P0
     OR P1 且 due 临近
     OR due 临近
     OR next_follow_up_at 临近 )

  问题
    一条"P1 + 无日期"的事项，任何一条都不满足
    → 它在 Today 上完全消失，只能去 Items 里翻
    → 用户会困惑："我明明标了高优先级，怎么首页没有？"

V1.3.1（修正）
  入选只看用户的显式标记：priority IN (P0, P1)
  "due 临近 / 最近有活动"这类推断只用于排序或直接删除

  因为
    P0 = 用户显式标"紧急"
    P1 = 用户显式标"高"
    用户显式设置的优先级，必须在 Today 上被尊重
```

被删除的规则（V1\.3）：

```Plain Text
近 3 天有工作记录
近 3 天有状态变化

原因
  "我昨天看了一眼"不等于"我今天要做"
  用"最近看过"当依据，是最容易让用户觉得
  "系统在猜我"的规则
  而一旦用户开始怀疑 Today 为什么这么排，
  整个首页的信任就没有了
```

为什么 P0 / P1 都无条件出现：

> P0 的语义是"紧急"，P1 的语义是"高"。
> 两者都是用户显式表达的优先级。
> 如果它们因为没有日期而不可见，
> 用户就会失去对"优先级"这个字段的信任，
> 也重新掉回"记录完就找不到"的老问题。

为什么这个区块必须保留（而不是像纯过滤器那样删掉）：

```Plain Text
如果 Today 只做确定性过滤：
  计划 / 逾期 / 到期 / 跟进 / 等待
        ↓
没有日期、非 P0/P1 的事项
        ↓
只能去 Items 里翻
        ↓
Today 退化成"瀑布列表"

保留 ⑥ 的价值：
  它是"捕漏"，不是"推荐"
  每条都必须能一句话解释为什么在这里
```

# Inbox

## 8\.1 产品目标

Inbox 是所有快速记录事项的临时入口。

原则：

> **先记录，再整理。**
> 
> 

用户不需要创建事项时填写完整字段。

---

## 8\.2 快速输入

支持：

```Plain Text
新建事项
```

只要求：

```Plain Text
标题
```

例如：

```Plain Text
跟进厂商接口问题
```

点击回车即可创建。

---

## 8\.3 Inbox 后续整理

两个入口（V1\.3\.4）

背景（来自场景 8）：

```Plain Text
我们的规则：Inbox 是处理队列 + 逐条整理 + 预算 30 秒/条
        ↓
堆了 30 条 = 15 分钟 + 60~90 次判断
        ↓
用户的选择一定是：关掉它，明天再说
        ↓
Inbox 变成只进不出的黑洞（正是我们想避免的）

根因
  我们只给了"每条都要你决定"的出口，
  没给"我一条都不想决定"的出口
```

所以 Inbox 顶部给两个入口：

```Plain Text
Inbox  7

[ 整理最老的一条 ]      ← 逐条，深入
[ 先都收下 ]            ← 批量，浅出
```

`先都收下` 的语义：

```Plain Text
把当前 Inbox 里的项一次性处理成：
  status   = TODO
  priority = P2（默认）
  project  = 空

效果
  它们离开 Inbox，进入 Items（默认视图"未完成"）
  之后可以在 Items 或项目里慢慢细化
```

由此调整一条旧规则：

```Plain Text
旧：整理完成条件 = projectId != null AND status != INBOX
新：整理完成条件 = status != INBOX

理由
  "整理"的本质是决定"它是不是一件要做的事"，
  不是"它属于哪个项目"
  项目归属可以之后补，甚至可以一直没有
  （日报里本来就有"未归属"分组）
```

为什么这条不违背"先记录，后整理"：

```Plain Text
"先收下"仍然是"整理"，只是整理得浅
它把用户从"每一条都要想清楚"里救出来
而 Inbox 的目标本来就不是"整理干净"，
而是"不要让想法烂在里面"
```

配套：必须有"未分类"计数（V1\.3\.5）

背景：

```Plain Text
30 条 Inbox
    ↓ 点击"先都收下"
变成 30 条 TODO / P2 / 无项目
    ↓
它们去哪？→ Items 的"未完成"（默认视图）
    ↓
有任何人提醒用户"你有 30 条没归项目的东西"吗？→ 没有

问题只是从"Inbox 黑洞"搬到了"Items 黑洞"
```

因此增加一个计数（不催、只显示）：

```Plain Text
未分类 30

定义
  project 为空 AND status NOT IN (DONE, CANCELLED)

显示位置
  1. Today 简报的"今日概览"里
  2. Items 的快捷筛选里（[未分类]）
```

规则：

> 它不提醒、不排序、不参与 Today 分区，
> 只是让这批东西保持可见。
> 否则"先都收下"会变成"先把问题藏起来"。

用户可以补充：

用户可以补充：

- 项目

- 类型（Task / Note）

- 优先级

- 日期

# Item 管理

删除语义："删除 = 取消"（V1\.3\.4 明确）

背景（来自场景 26）：

```Plain Text
用户想删掉一条记错的、已经整理过的事项
        ↓
但规则是"已整理过的不物理删除，只能取消"
        ↓
他点了"删除"，结果它变成"已取消"还在列表里
        ↓
用户会认为："删不掉" / "系统坏了吧"
```

所以界面文案必须提前说清，而不是让用户去试：

```Plain Text
Item 的 ⋯ 菜单
  ❌ 删除
  ✅ 取消事项
      说明："已取消的事项会留在"所有记录"里，不会被删掉"

真正删除只对"还没整理过的条目"开放
  （status = INBOX 且从未产生记录）
  菜单文案："删除这条记录"
```

原则：

> 数据的可追溯性优先于"删干净"，
> 但我们不能靠"用户点了才知道"来实现它。

## 9\.1 Item 列表

支持：

```Plain Text
全部
任务（TASK）
记录（NOTE）

按状态筛选
  待整理 / 待办 / 进行中 / 等待中 / 已完成 / 已取消

按能力筛选（V1\.3）
  跟进中（next_follow_up_at 非空）
  待跟进（next_follow_up_at <= now）
  等待中（status = WAITING）
  今日计划（planned_date = 今天）
  未计划（planned_date 为空）

默认视图（V1\.3\.2 修正）
  未完成（status NOT IN (DONE, CANCELLED)）

  原因
    "所有记录"的默认视图若是"未计划"，
    用户会以为系统漏了数据
    "未计划"降为快捷筛选
```

说明（V1\.3）：

> "等待 / 同步 / 提醒" 不再是类型，而是状态或独立对象。
> "跟进"也不再是类型，而是能力（`next_follow_up_at` 非空）。

支持筛选：

```Plain Text

状态
优先级
日期（包含"无日期"）
```

说明（V1\.3\.3）：

> 去掉"按人员筛选"。
> "人"只作为自由文本存在，不做筛选维度，
> 否则会自然长出一个人员实体模型。

注意：

> MVP 不做 Tag。
> 有了项目 + 类型 + 状态 + 优先级 + 日期，
> 标签只会变成第二套分类系统。

# Item 状态机

MVP 状态与合法转换：

```Plain Text
INBOX      → TODO, CANCELLED
TODO       → DOING, WAITING, DONE, CANCELLED
DOING      → TODO, WAITING, DONE, CANCELLED
WAITING    → TODO, DOING, DONE, CANCELLED
DONE       → TODO
CANCELLED  → TODO
```

说明：

```Plain Text
DONE → TODO        撤销完成 / 重开

```

# 优先级

MVP 提供：

```Plain Text
P0 紧急
P1 高
P2 普通
P3 低
```

语义补充（V1\.3\.2）：优先级要说清"什么时候用"，否则最后所有事都是 P1。

```Plain Text
P0  不处理会产生立即影响
      生产问题、今天必须给人回复、阻塞别人的事

P1  本周期必须主动推进
      这周要交的东西、要推动的人

P2  正常工作
      排期内的常规任务

P3  有空再做
      想法、优化、可选事项
```

界面上的辅助说明（避免"所有事都是 P1"）：

```Plain Text
选 P0 时提示：不处理会有什么影响？
选 P1 时提示：是这周要推进的事吗？
```

为什么加这段（V1\.3\.2）：

```Plain Text
如果 P1 只表示"重要"，
一个项目里最终会有 8 条 P1 一起进"待安排"，
用户又回到"那我到底先做哪个？"

优先级必须成为用户做决策的语言，而不只是颜色。
```

优先级与截止日期独立。

例如：

```Plain Text
P1
截止日期：下周
```

表示重要但不一定今天处理。

## 五种时间语义（V1\.2 新增）

一个 Item 最多涉及五种时间，必须区分清楚，否则用户会问
"到底哪个时间是我今天该处理的？"

| 时间 | 回答的问题 | 是否影响 Today |
|---|---|---|
| planned_date | 我计划哪天做 | 是（① 今日计划） |
| due_at | 最晚什么时候完成 | 是（② 逾期 / ③ 今日到期） |
| next_follow_up_at | 我什么时候再次主动推动 | 是（④ 待跟进） |
| waiting_expected_at | 对方预计什么时候给结果 | 否（只在等待中打"对方逾期"标记） |
| reminder.remind_at | 系统什么时候提醒我 | 否（它是通知机制，不是业务时间） |

关键规则：

```Plain Text
Reminder 不是业务时间
  它由业务时间派生：due_at / next_follow_up_at → remind_at
  删除提醒不影响事项状态

waiting_expected_at 不改变分区归属
  否则会和"待跟进"重复计数
  它只产生一个标记 + 一条"需要你决定"
```

## 时区与日界（V1\.1 新增）

WorkOS 大量逻辑围绕"今天"：

```Plain Text
Today 的各分区
逾期判断
待跟进判断
日报归属哪一天
```

因此必须明确两件事：

```Plain Text
时区
  由 Settings 配置
  是"今天"的唯一真源

日界
  凌晨工作归属哪一天

  MVP 默认：0 点（即 00:00 算新的一天）
  字段保留，但**暂不开放给用户修改**
```

规则：

> 不允许写死时区，也不允许用服务器 UTC 日期代替用户所在时区的"今天"。

时区的初始值（V1\.3\.3 修正）

背景：

```Plain Text
如果产品默认写死 Asia/Shanghai
        ↓
换一台在美国的机器、或浏览器在别的时区
        ↓
服务器认为今天是 A 日
浏览器认为今天是 B 日
        ↓
Today / 日报 / work_date 全部错位
```

正确做法：

```Plain Text
首次启动
    ↓
读取系统 / 浏览器时区
    ↓
写进 settings.timezone
    ↓
用户之后可以自己改
```

说明：

> 我们的用户主要在国内，结果是"自然得到 Asia/Shanghai"，
> 但"默认值"不应该由产品拍定，而应该由环境决定。

V1\.3\.2 修正：日界线不进 MVP 界面

```Plain Text
旧版：默认 4 点，凌晨工作归前一天

问题
  这条规则贯穿 Today / Daily / 工作记录日期 / 统计
  一旦实现，就要处理
    23:59 / 00:30 / 03:59 / 04:00
    时区切换 / 夏令时
    Tauri / 浏览器 / 服务器 三处一致

  而"凌晨加班要算昨天"这个习惯，
  目前还没有任何真实用户验证

新版
  MVP：日界线 = 0 点（自然日）
  Settings 里不出现这个选项
  字段保留，等真实用户提出需求再开放

原则
  不要为一个尚未验证的使用习惯，
  给整个系统增加时间计算复杂度
```

## 上下文保鲜（V1\.1 新增）

Context 是产品最容易被"用旧"的部分。

如果用户不主动维护，几周后它就会过期，"10 秒恢复上下文"随之失效。

因此必须由系统主动提醒：

```Plain Text
规则一：过期提示
  Context 超过 14 天未更新
        ↓
  项目卡片与详情页显示"上下文已 14 天未更新"

规则二：关键事项完成时提示
  项目中的 P0/P1 或 DOING 事项被完成
        ↓
  轻提示（非弹窗，不打断当前工作）
        ↓
  "工单自动分配已完成，更新当前重点 / 下一步？"
        ↓
  点击进入 Context 编辑，并预填已完成事项标题

规则三：完成时顺带记录进展（可选）
  完成关键事项时，可一键把事项标题追加到"当前进展"
```

验收：

```Plain Text
连续使用两周后，Context 仍能反映项目真实状态
且用户不需要"记得去更新"
```

## 18\.2 自动生成

系统根据：

- 今日完成任务

- **人工** Work Log（`source = MANUAL`）

- Follow\-up 与 Waiting 的**今日变化**（不是当前状态快照）

生成初始日报。

用户可以继续编辑。

系统事件（Activity）与日报的关系（V1\.3\.2 修正）：

```Plain Text
进入日报
  DONE 事项（今日完成）
  人工 WorkLog（今日工作记录）
  Follow-up / Waiting 的今日变化（跟进与等待）

不进入日报的"工作内容"
  Activity（创建 / 开始 / 状态变化等系统事件）

但 Activity 可以用来**判断变化**
  "今天是否进入 Waiting"
  "今天是否退出 Waiting"
  "今天是否真的跟进过"
        ↓
  决定"跟进与等待"区块写什么
```

理由：

```Plain Text
一、系统事件不能当"工作内容"
    否则日报变成流水账：
    "10:01 创建任务 → 10:15 进入 Doing → 14:30 完成"

二、但"跟进与等待"必须是"今天的变化"，不是"当前的状态"
    否则会出现：
      9/20 等待厂商接口
      9/21 等待厂商接口
      9/22 等待厂商接口
      9/23 等待厂商接口
    每天一样的四行，没有任何信息量

    要实现"只写变化"，生成器就必须读 Activity
```

另外，计划数据以 Item 为真源（V1\.2）：

```Plain Text
Item.planned_date  = 计划的唯一真源
Daily 中的"明日计划" = 生成出来的表达

用户在 Markdown 里改"明日计划"
  → 只当作文本，不回写 Item
计划变更请通过"确认明日计划"按钮（写 planned_date）
```

分组规则（V1\.3\.1 补齐）：

```Plain Text
按项目分组

project_id 为空的事项
        ↓
统一归入"未归属"分组
        ↓
排在所有项目分组之后
```

原因：

> 一天做 10 件杂事时，这些事很可能都没有项目。
> 没有这条规则，日报会散成一堆条目，反而更难读。

生成方式：增量补充，不是重新生成整篇（V1\.3\.3）

背景：

```Plain Text
12:00 用户点了一次"生成"
15:00 又完成两件事
17:00 又写了一条工作记录
18:00 再点一次
        ↓
用户会担心："会不会把我上午改的覆盖掉？"

虽然模型里已经写了"不覆盖 content"，
但用户不应该需要理解这件事。
```

所以界面不叫"生成 / 重新生成 / 应用"，而是：

```Plain Text
今天的日报

[已有内容]

────────────────────

新增的工作事实

今天完成：
+ 工单接口

新增记录：
+ 与产品确认范围规则

────────────────────

[ 更新日报草稿 ]
```

语义变化：

```Plain Text
❌ 生成 → 替换
✅ 新增事实 → 补充到草稿
```

好处：

```Plain Text
用户随时可以点，不会有"会不会覆盖"的心理负担
多次点击的语义是累加，而不是重置
```

日报页面增加"本周"切换（V1\.3\.4）

背景（来自场景 25）：

```Plain Text
用户想回顾"上周我干了什么"
        ↓
只能进 Daily，一天一天翻
        ↓
3 个角色里，这个场景的耗时为 80~90 秒
        ↓
而"长期工作档案"是我们的核心承诺之一
```

做法（不是做周报）：

```Plain Text
Daily 页面顶部

[ 日 ] [ 周 ]

选"周" → 只读聚合视图：
  本周完成（按项目分组）
  本周记录（按天列出）
  本周跟进与等待的变化
```

边界：

```Plain Text
不做：周报生成、周报模板、周报提交
只做：把本周已经存在的事实聚合出来
真正的周报仍属 V2（产品演进路线里已有）
```

## 18\.3 收工复盘与计划结转

日报页面同时承担"收工复盘"职责。

```Plain Text
每日收工时间提醒一次："今天收个尾？"

收工复盘包含：
  1. 今日完成（自动汇总）
  2. 未完成计划 → 逐条处理：
        结转到明天 / 改期 / 转 Waiting / 取消
  3. 工作记录（自动汇总）
  4. 跟进与等待
  5. 明日计划候选（来源：未完成结转 + 明日到期 + 今日新增未计划）
```

未完成计划的口径（V1\.3\.1 修正）：

```Plain Text
planned_date < 今天
AND status NOT IN (DONE, CANCELLED)

不是"只有昨天"
  如果用户 9/22 计划了 3 件，
  9/23 没打开，9/24 才打开
        ↓
  按"昨天"口径 → 9/23 没有计划 → 什么都不提示
  9/22 的 3 件欠账就彻底消失了

必须显示老化程度
  "2 项未完成（其中 1 条是 3 天前计划的）"
```

不做自动结转。

理由：

> 自动结转会让"今日计划"永远完不成，计划本身的意义消失。
> 必须由用户做一次显式取舍。

图片处理的边界（V1\.3）：

```Plain Text
MVP 支持
  ![alt](https://...)
  引用外部图片地址

MVP 不做
  图片上传
  （需要文件存储、清理、备份、容量管理，
    对个人自部署场景不划算）
```

因此编辑器里不提供"上传图片"按钮，只接受 URL。
需要长期保存图片时，把它放在自己的图床或网盘。

# Calendar

MVP 不做，后置到 V1\.1（V1\.3 决定）。

```Plain Text
MVP 暂不提供 Calendar
V1.1 提供：月视图 + 点击某天打开 Day 面板
```

为什么可以不做：

```Plain Text
Calendar 的价值 = 从时间维度看事项

这个价值已经被覆盖：
  Today            今天该做什么
  Items 日期筛选    某天到期 / 某天计划
  Daily            某天做了什么
  Follow-ups 区块   本周要跟进什么

而它对"愿意每天打开"没有贡献
```

# Reminder

提醒包括：

## 任务提醒

```Plain Text
09:30
开始处理工单分配
```

## 截止提醒

```Plain Text
17:00
工单分配今日截止
```

## Follow\-up

```Plain Text
10:00
该催张三了：接口方案
```

注意文案（V1\.3\.2 修正）：

```Plain Text
❌ 待跟进：厂商接口问题        （只有事项名，没有"人"）
❌ 你答应张三今天回复接口方案   （系统替用户断言承诺，过度）
✅ 该催张三了：接口方案        （事实：我在等，到点该催）

原因
  第一条丢掉了"在等谁"
  第二条写过了头，把 due_at 当成了承诺
  第三条是事实陈述，模型完全支持

  让人愿意打开 WorkOS 的，
  是"有一个人、一个时间在等我"，
  而不是一句系统编出来的承诺
```

这条文案规则直接服务 K2（漏跟率）与"愿意每天打开"：

> 有具体的人 + 具体的时间，比抽象的事项名更能推动行动。

文案推导规则（V1\.3\.2 修正，不新增字段）：

```Plain Text
模型里没有"承诺方向"字段，所以不能凭空断言承诺。

① 别人欠我（这是事实，可以说）
     status = WAITING
     AND waiting_for 非空
     AND next_follow_up_at <= now
        ↓
   "该催 {waiting_for} 了：{title}"

② 我和某人相关（中性陈述）
     related_person 非空
     AND due_at 临近
        ↓
   "{related_person} · {due_at} 前 · {title}"

③ 不要写成
   "你答应 {related_person} 在 {due_at} 前 {title}"
```

为什么推翻 V1\.3\.1 的写法：

```Plain Text
due_at 可能只是我自己定的内部截止，
并不代表我对谁承诺过。

系统替用户说出"你答应了"，
就是"文案比数据模型表达得更强"——
用户会立刻觉得系统在瞎编。
```

原则（V1\.3\.2）：

> **文案不能比数据模型表达得更强。**
>
> "你答应"这种话，只能出现在用户自己写的标题里，
> 不能由系统生成。

两种情况都不需要新增字段：

```Plain Text
差别只在"这条是不是 WAITING"
不再依赖对 due_at 的语义猜测
```

```Plain Text
18:00（可在 Settings 调整 eod_review_time）
今日日报还未完成
```

## 提醒通道与兜底

提醒必须闭环，不能依赖"用户正好开着 App"。

```Plain Text
通道一  应用内提醒
        打开 App 时，到期的提醒立即展示

通道二  桌面 / 浏览器通知
        Tauri 原生通知，或浏览器 Notification

通道三  启动补偿（关键）
        打开 App 时，把已到期但未送达的提醒
        聚合成"你需要处理的提醒"清单
        展示在早晨简报顶部
```

MVP 不承诺"App 关闭时的后台推送"。

因此：

> **启动补偿 \+ 早晨简报，才是"不漏跟"的主保障。**

状态模型（V1\.3 简化）：

```Plain Text
PENDING      待处理（还没被用户处理）
DISMISSED    这次提醒已处理（注意：不等于业务已处理）
CANCELLED    已取消

另外记录
  acknowledged_at 用户处理这次提醒的时间
```

后台调度（V1\.3\.3 取消）

背景：

```Plain Text
MVP 没有外部推送渠道（不做邮件 / 短信 / IM）
        ↓
后端 10:00 扫描并"触发"提醒
        ↓
但这个触发不会真正通知到任何人
        ↓
那这次扫描有什么意义？
```

所以 MVP 把提醒交给客户端驱动：

```Plain Text
打开 App
    ↓
查询：status = PENDING 且 remind_at <= now
    ↓
展示（这就是启动补偿）

App 前台运行时
    ↓
每 30~60 秒查询一次

Tauri 装好后
    ↓
本地通知由客户端调度
```

好处：

```Plain Text
架构里少一个后台调度器
不再需要"服务端触发时间"这种没人消费的字段
以后真接了外部渠道，再把调度加回来也不难
```

为什么去掉"已送达"：

```Plain Text
服务器触发 ≠ 通知送达 ≠ 用户看到 ≠ 用户处理

用"触发"冒充"送达"是自欺
而 MVP 本来就不承诺送达

所以：
  应该提醒 = PENDING 且 remind_at <= now
  启动补偿 = 这一条查询
  不需要判断"用户到底看没看到"
```

原则：

> **绝不能让 Reminder 成为 Follow-up 是否存在的依据。**
> Reminder 是通知增强机制，Follow-up 是业务事实。

## 28\.3 item

```Plain Text
item
------------------------
id
project_id

title
description

item_type         TASK | NOTE
status            INBOX | TODO | DOING | WAITING | DONE | CANCELLED
priority          P0 | P1 | P2 | P3

planned_date      我计划哪天做
plan_rank         今日计划顺序
due_at            最晚什么时候完成
next_follow_up_at 我什么时候再次推动（非空 = 跟进能力）

waiting_for        在等谁（自由文本，进入 Waiting 时必填）
waiting_since      什么时候开始等
waiting_expected_at 对方预计什么时候给

related_person     相关人（自由文本，一个字段；V1.3.3 起不再有 related_company）

created_at
updated_at
completed_at
cancelled_at
version
```

字段说明（V1\.3）：

```Plain Text
已删除 parent_id
  它等于偷偷引入子任务
  一旦有父子，就要回答：
    父任务完成条件？子任务进不进 Today？
    父任务是否自动完成？Waiting 挂父还是挂子？
    Daily 记录谁？
  MVP 不引入这个分支

Follow-up 不再是 item_type
  next_follow_up_at 非空 即表示"这是一条跟进事项"
```

关于"人"的字段（V1\.3\.3 收敛）

背景：

```Plain Text
同时存在 related_person 与 waiting_for
        ↓
"等待张三确认方案" 会存两遍同一个名字
        ↓
又出现"张三 / 张 三 / 张三（产品）/ 张三-产品"
        ↓
开始变成一套轻量人员模型（脏数据 + 想做筛选 + 想做实体）
        ↓
Person / Company / Contact / Department 就这样溜进 V1
```

收敛规则：

```Plain Text
删除 related_company        （它没有任何产品角色）
不建 Person / Company 实体
不做"按人员筛选"            （避免它变成人员维度的入口）

只保留一个自由文本字段：相关人
  不枚举、不联想、不校验
  进入 Waiting 时，默认把"相关人"带成等待对象，不用填第二遍
```

为什么不能把"人"整个删掉：

```Plain Text
"我在等谁 / 我该催谁" 是 WorkOS 的头号差异点
非等待类的跟进（"周三问问张三进度"）也需要一个具体的人
删掉之后文案只能退回"待跟进：接口方案"，丢掉人
```

# 后端技术选型

MVP：

```Plain Text
Java 21
Spring Boot 3.x
MyBatis-Plus
PostgreSQL
```

明确不引入（V1\.3）：

```Plain Text
Redis
  Search 用 PostgreSQL pg_trgm
  Session 用本地单用户身份
  没有需要缓存的热点数据

  没有外部推送渠道时，"后端触发"不会真正通知到任何人
  提醒改由客户端驱动：
    打开 App → 查询 PENDING 且已到期
    前台运行时 → 每 30~60 秒查一次
  Tauri 装好后，本地通知也由客户端调度

对象存储 / 文件服务
  Markdown 不支持图片上传

以后触发条件：
  多用户 + 多设备会话 → 再评估 Redis
```

# 用户与身份（V1\.3）

MVP 的定位是**个人工作台**，但系统形态是 Web \+ Tauri \+ 服务端，
所以必须有最小身份模型，否则部署之后谁都能读写。

定位：

```Plain Text
单用户自部署
  一个 WorkOS 实例 = 一个用户
```

做法：

```Plain Text
必须有
  本机访问     免登录（本地回环地址）
  非本机访问   必须登录
  登录方式     用户名 + 密码（或一次性令牌）
  会话         Cookie / Token，服务端可撤销

不做
  注册流程 / 多用户
  角色 / 权限 / RBAC
  团队 / 组织 / 租户
  OAuth / SSO
```

数据结构：

```Plain Text
account
------------------------
id
username
password_hash
created_at
updated_at
```

产品约束（重要）：

> **认证不能成为打开工作台的单点故障。**
>
> 个人工具最糟的体验是"登录坏了，我打不开自己的工作计划"。
>
> 因此：
>   本机访问免登录
>   登录凭证可重置（有文档化步骤）
>   不做强制改密 / 过期 / 验证码等企业策略

未来 V2 再评估：

```Plain Text
User / Organization / Role
多设备同步的会话管理
```

```Plain Text

DELETE /api/items/{id}/plan

GET    /api/today

GET    /api/search

GET    /api/settings

GET    /api/export
```

说明（V1\.3）：

```Plain Text
/transitions 是唯一的状态变更入口，可携带业务载荷：
  {
    "toStatus": "WAITING",
    "waitingFor": "厂商A",
    "waitingExpectedAt": "...",
    "nextFollowUpAt": "..."
  }

已删除（V1.3）
  /complete   等价于 transitions { toStatus: DONE }
  /waiting    等价于 transitions { toStatus: WAITING, ... }
  /follow-up  等价于 PUT /items/{id} { nextFollowUpAt }

原因
  一边声明"唯一状态变更入口"，
  一边并排三个 action 端点，是自相矛盾
  而且会让 Follow-up 在 API 层再次"实体化"

前端可以在 api/item.ts 里包 convenience 函数，
但 HTTP 契约只保留 transitions 与 PUT
```

# 数据存储原则

结构化字段：

```Plain Text
项目
状态
优先级
日期
提醒
```

进入数据库字段。

非结构化内容：

```Plain Text
描述
日报
项目 Context
工作记录
备注
```

使用 Markdown。

原则：

> **不要把所有内容都塞进 Markdown，也不要把所有内容都结构化。**
> 
> 

四个对象谁是"事实真源"（V1\.3\.3 明确）

这是最容易在实现阶段被搞混的地方，所以直接写成四句话：

```Plain Text
Item      是"事项状态"的事实真源
WorkLog   是"人的工作"的事实真源
Activity  是"系统变化"的事实真源

Context   不是事实真源，它是项目当前状态的人工摘要
Daily     不是事实真源，它是某一天的最终表达
```

由此推出四条禁止：

```Plain Text
❌ 改 Daily   反过来修改 Item
❌ 改 Context 自动修改 Item
❌ Activity   自动生成 WorkLog
❌ Daily      被当成"今天到底做了什么"的唯一依据
```

为什么必须写死：

> 否则研发很容易做出"改日报顺手更新事项"这类方便的实现，
> 最后数据互相污染，谁也说不清哪个是真的。

---

## 数据可信：备份与导出（V1\.1 新增）

产品承诺"形成长期工作档案"，因此数据必须可信、可带走。

MVP 必须提供：

```Plain Text
备份
  每日自动 pg_dump
  必须写到与数据库**不同的存储位置**
  保留最近 14 份

导出
  Markdown：按项目分目录，含 Context + 事项 + 日报
  JSON：全量数据

恢复
  文档化步骤，可在新机器还原
```

理由：

> 没有备份与导出，用户不敢把重要工作长期交给它。
> 这不仅是技术问题，也是产品信任问题。

两条硬要求（V1\.3）：

```Plain Text
一、备份必须独立存储
  数据库和备份在同一块盘 = 没有备份
  盘坏了会同时丢掉两者

二、验收标准是"能恢复"，不是"执行了备份"
  新库能启动
  数据条数基本一致
  Item 与 Daily 可读
  恢复步骤可被另一个人照做
```

导出还要满足"人可读"：

```Plain Text
打开导出的 Markdown
        ↓
能直接看懂"这个项目现在是什么状态"
        ↓
而不是一堆 JSON 字段
```

## 手机端：只读 + 速记（V1\.3\.4 新增）

背景（来自场景 28）：

```Plain Text

  会议室、客户现场、工位之间来回
        ↓

        ↓
"想看一眼今天的事" 或 "想到一句要记下来"
在手机上直接做不到
        ↓
这不是体验问题，是硬伤
```

范围（严格限定）：

```Plain Text
手机端能做
  打开 Today（只读：今天做什么 / 今天别忘了 / 我在等谁）
  快速记录一句（本地暂存 + 联网提交）

  整理 Inbox
  编辑事项 / 改状态 / 改优先级
  写日报
  管理项目
```

理由：

```Plain Text
手机是"看"和"记"的设备，不是"整理"的设备
把整理搬上手机，会引出第二套交互（拖拽、多选、抽屉）
而我们只需要堵住"看不了、记不下"这两个洞
```

技术要求：

```Plain Text
响应式布局下探到手机宽度（约 375px 起）
桌面端仍然是主要工作界面
```

## 37\.13 首次使用（V1\.3 新增）

用户第一次打开（数据库为空时）能看到：

```Plain Text
一个引导页，两个选择：
  [ 用示例体验一下 ]
  [ 直接开始工作 ]

选"体验" → 写入示例项目 + 3 条示例事项 + 示例 Context
选"直接开始" → 干净的空白工作区
```

理由：

> 空产品没有价值，用户第二天不会打开。
> 这是"愿意每天打开"的第一道门。

为什么示例数据不能默认混进工作区（V1\.3\.3）

背景：

```Plain Text
第一次打开就是"示例项目 + 3 条示例事项"
        ↓
用户分不清"哪个是我的、哪个是示例的"
        ↓
对个人工作工具来说，"混着假数据"比"空着"更糟
```

所以默认是**空工作区**，示例只在用户主动选择时才创建。

三条实现细节（V1\.3\.1 补齐）：

```Plain Text
① 相对日期生成
     示例事项的 due_at / planned_date 必须以"今天"为基准
     否则用户第二天打开，会看到一堆"逾期"的示例

② 可识别 + 可清除
     示例项目要能被识别（如 code = DEMO）
     并提供"清空示例数据"按钮
     避免用户把示例当成真实数据

③ 埋点排除
     K1 捕获延迟 / K4 日报准备时间的样本必须排除 demo 数据
     否则第一批指标全被污染
```

## 37\.14 带"人"的文案（V1\.3 新增，V1\.3\.2 修正）

提醒与跟进区块的文案必须带上**具体的人**，但不能替用户断言承诺：

```Plain Text
❌ 待跟进：厂商接口问题        （丢掉了"在等谁"）
❌ 你答应张三今天回复接口方案   （系统替用户断言，过度）
✅ 该催张三了：接口方案        （事实陈述）
✅ 张三 · 今天 18:00 · 工单接口 （中性陈述）
```

理由：

> 让人愿意打开 WorkOS 的，是"有一个人、一个时间在等我"。
> 但"你答应了"这种话，只能由用户自己写，不能由系统生成。

文案推导规则见 5\.4 与 Reminder 一节：

# 产品核心原则

WorkOS 后续所有功能设计遵循以下原则：

### 原则一：快速记录优先

不要让用户为了记录一件事情填写十几个字段。

---

### 原则二：先记录，后整理

Inbox 允许不完整信息。

---

### 原则三：任务和等待同等重要

“我需要做什么”和“我在等什么”必须同时被管理。

---

### 原则四：项目是上下文，不是文件夹

项目应该帮助用户恢复工作状态。

---

### 原则五：日报来源于工作，而不是重新创造工作

日报应该由已完成的事项与（可选的）工作记录自动汇总。

注意（V1\.3\.2）：

> 不能把"写工作记录"变成日报的前置条件。
> 用户没写工作记录，日报仍然要有东西可看——
> 那就是"今天完成了哪些事项"。

---

### 原则六：结构化数据和 Markdown 并存

结构化信息负责管理。

Markdown 负责表达。

---

### 原则七：降低上下文切换成本

任何项目都应该能够在 10 秒内恢复上下文。

---

### 原则八：功能评审门禁（V1\.2 新增）

从 V1\.2 起，任何新功能进入 MVP 前必须回答一个问题：

> **它是否直接帮助用户完成以下核心动作之一？**

```Plain Text
捕获
判断
执行
等待
跟进
记录
复盘
```

如果不能，或者理由只是：

```Plain Text
以后可能有用
别人也有这个功能
顺手就做了
```

则不进入 V1。

第二条门禁（V1\.3\.1）：素人测试

> **每个功能都必须能用一句素人听得懂的话说清楚。**
>
> 说不出来 → 要么改文案，要么砍掉。

原因：

```Plain Text
写不出"用户语言"，通常意味着两种情况之一：
  一、这个功能对用户其实没有价值（那就砍）
  二、这个功能有价值，但我们用行话在描述它（那就改文案）

两种都不该带进 V1。
```

执行方式：

```Plain Text
第 6 章「功能背景与意义」的每一节都有"用户语言"一行
任何新增功能，必须同时补上这一行
```

背景：

> WorkOS 已经包含 Project / Context / Item / Waiting / Follow-up /
> WorkLog / Daily / Search / Reminder / Settings 等能力，
> 再往上加（标签体系、人员、厂商、模板、周报、Dashboard、AI）
> 会迅速退化成
> "Notion + Todoist + Jira + 日报系统"。

---

### 原则九：一个 Item = 一个可闭环事项（V1\.3 新增）

```Plain Text
一条 Item 必须能被"关闭"：
  做完 → DONE
  不做 → CANCELLED

如果一件事内部包含多个可独立关闭的步骤，
那它就是多条 Item，而不是一条"工作流容器"
```

反例：

```Plain Text
❌ 工单自动分配功能
   内部包含：数据库 / 接口 / 前端 / 联调 / 测试
   → 无法关闭，也无法判断做到哪

✅ 完成工单数据模型
✅ 完成工单接口
✅ 完成前端页面
✅ 联调工单接口
```

为什么这条重要：

```Plain Text
它决定了 Waiting 是否成立
  "等待厂商接口" 必须是独立 Item
  否则一条大任务卡住时，整条任务都不能进入 DOING

它也是删除 parent_id 的前提
  没有 subtask，就不需要回答父子任务的六个产品问题
```

代价与对策：

```Plain Text
代价
  过度原子化会让 Inbox 变多，整理成本上升

对策
  在 Inbox 与 Item Drawer 里给出"要不要拆开"的轻提示
  但不引入 subtask 机制
```

边界（V1\.3\.2）：

```Plain Text
"一个 Item = 一个可闭环事项"不等于"一个技术步骤一个 Item"

判断标准不是"能不能拆"，而是：
  它是否需要独立进入我的注意力系统？

反例（不该拆）
  完成工单自动分配功能
    内部含 数据库 / 接口 / 前端
    这些是同一件事的工作步骤，不是一个一个要独立关闭的事项

正例（该拆）
  等待厂商提供接口文档
    它需要独立跟进、独立设等待对象与跟进时间
```

---

### 原则十：用户只记录事实一次，系统负责重新组织（V1\.3\.2 新增）

这是本轮减负修订的总纲：

> **能从已有事实推导出来的，就不要让用户再输入一次。**

反例：

```Plain Text
❌ 已经完成 Item，还要求写一条 WorkLog"完成 XX"
❌ 已经设了 next_follow_up_at，还要求再设一个同时间 Reminder
❌ 已经有今天的完成事项，还要用户在日报里重新输一遍
❌ 已经填了 focus / blocker / next_action，还要求手写一句"当前进展"
```

正例：

```Plain Text
✅ 完成后只在用户想补一句时提供入口，不强制
✅ 跟进时间到期 → Today 自动出现，不额外要提醒
✅ 日报从"已完成事项 + 可选工作记录"生成
✅ "当前进展"由系统给默认文本（最近完成 / 正在进行），用户改两个字即可
```

为什么这条排在前十：

```Plain Text
WorkOS 最大的失败模式不是功能不够，
而是"用户每天要维护的东西太多，
最后干脆不维护了"。

本原则用来在每次评审时挡住新的维护动作。
```

---

### 原则十一：显式优先于推断（V1\.3\.3 新增）

> **WorkOS 不猜用户，只呈现用户已经表达的事实。**

用户显式设置的东西，一定有明确含义：

```Plain Text
设置 planned_date      → 一定表示"我打算今天做"
设置优先级 P1          → 一定表示"我认为它重要"
设置 next_follow_up_at → 一定表示"我需要跟进"
进入 WAITING           → 一定表示"我在等别人"
```

系统不能因为：

```Plain Text
"最近 3 天没动"
"最近看过"
"看起来快到期了"
```

就推断"应该关注它"。

我们前面已经按这条原则删掉的规则：

```Plain Text
近 3 天有 Activity    → 删
近 3 天有 WorkLog     → 删
"已完成跟进"当作实体   → 删
```

为什么这条重要：

```Plain Text
规则一多，产品就变成规则引擎：
  用户输入 5 个字段
  → 系统推理 17 条规则
  → 系统猜用户想做什么

而一旦用户开始怀疑"它为什么把这条放到这"，
整个首页的可信度就没了。

Today 尤其如此：每条出现在今天的事项，
用户都要能一句话说出"它为什么在这里"。
```

例外：

```Plain Text
"排序"可以使用推断（谁在前面）
"入选"只能用显式事实（要不要出现）
```

---

### 原则十二：环境对象 ≠ 领域对象（V1\.3\.5 新增）

> **用户工作环境里存在的东西，不一定都要成为 WorkOS 的领域对象。**

背景：

```Plain Text
把真实的一天拆开，会看到：
  会议 / 消息 / 需求 / BUG / 发布 / 领导 / 客户 / 厂商

它们确实全部存在。
但"存在"不等于"要在 WorkOS 里建实体"。

（前几轮已经三次有人提出要加
   Meeting / Person / Decision / Risk / Release，
   每次都靠"这个场景很真实"来推。)
```

判断方式：

```Plain Text
会议
  ✅ 一条 Item："上午 10 点和产品确认工单范围"
  ❌ Meeting / MeetingParticipant / MeetingMinutes
     / MeetingDecision / MeetingAction

需求
  ✅ 一条 Item + 描述里的理由
  ❌ Requirement / RequirementVersion / DecisionChain

厂商 / 联系人
  ✅ 一个自由文本"相关人"
  ❌ Person / Company / Contact / Department

风险
  ✅ Context.blocker（用户自己写）
  ❌ Risk 实体 + 自动识别
```

一句话判断：

```Plain Text
如果它能用"一条事项 + 一句描述"表达 → 不要建实体
只有当它需要独立生命周期、独立筛选、独立权限时 → 才考虑建实体
```

为什么把它排进核心原则：

```Plain Text
真实的一天很复杂，这是事实
但"因为真实很复杂"是最容易把产品做成
飞书 / 钉钉 / Notion 的一条路

本原则用来在每个"要不要加实体"的讨论里先挡一次
```

# MVP 一句话定义

> **WorkOS 是一个以“项目上下文”为核心、以“事项追踪”为主线、以“工作记录和日报”为沉淀的个人工作操作系统。**
> 
> 

其核心闭环：

```Plain Text
捕获
 ↓
整理
 ↓
决策
 ↓
执行
 ↓
等待
 ↓
跟进
 ↓
记录（完成事项 + 可选的工作记录）
 ↓
日报
 ↓
沉淀
 ↓
再次进入上下文
```

两处说明（V1\.3\.2）：

```Plain Text
一、加了"决策"
   用户不是"整理完就直接执行"，
   中间一定有一次"今天做哪几件 / 要不要接手"的判断。
   Today 就是承载这一步的地方。

二、"记录"不再等于"写工作记录"
   完成 Item 本身就是记录。
   工作记录是增强项，不是必经步骤。
```

这就是 WorkOS MVP 的产品核心。
