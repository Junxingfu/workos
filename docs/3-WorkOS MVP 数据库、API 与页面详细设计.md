# 一、MVP 产品核心模型重新确认

WorkOS 不应该做成 Jira、Notion、Trello 的简单拼接。

MVP 的核心价值是：

> **让我知道“现在有什么事情、事情属于哪个项目、下一步要做什么、在等谁、什么时候跟进，以及今天到底干了什么”。**
> 
> 

因此核心对象保持如下：

```Plain Text
Project
   │
   ├── Project Context
   │
   ├── Item
   │     ├── Task
   │     ├── Follow-up
   │     ├── Waiting
   │     ├── Sync
   │     ├── Reminder
   │     └── Note
   │
   ├── WorkLog
   │
   └── Daily
```

其中：

特别注意：

> **Item ≠ WorkLog ≠ Daily**
> 
> 

例如：

```Plain Text
Item：
跟进XX厂商接口问题

WorkLog：
今天与厂商技术人员沟通，确认是接口字段定义不一致

Daily：
今日主要处理XX项目接口联调问题……
```

三个对象描述的是三个不同维度。

# 三、数据库统一规范

## 3\.1 主键

统一使用：

```SQL
BIGINT
```

MVP 推荐使用 PostgreSQL：

```SQL
BIGINT GENERATED BY DEFAULT AS IDENTITY
```

例如：

```SQL
id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

暂时不使用 UUID。

原因：

个人系统内部数据量很小，BIGINT 更简单。

未来如果需要：

- 多端同步

- 离线创建

- 多数据库合并

再考虑 UUID / ULID。

# 六、project\_context 表

这是 WorkOS 与普通 Todo 系统非常重要的区别。

```SQL
CREATE TABLE project_context (
    id                  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

    project_id          BIGINT NOT NULL,

    -- 稳定信息（几乎不变）
    goal                TEXT,

    key_people          TEXT,

    key_links           TEXT,

    -- 动态状态（会变，需要保鲜）
    focus               TEXT,

    blocker             TEXT,

    next_action         TEXT,

    progress_note       TEXT,

    -- 可选补充
    notes_markdown      TEXT,

    updated_at          TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    version             INTEGER NOT NULL DEFAULT 0,

    CONSTRAINT uk_project_context_project
        UNIQUE (project_id),

    CONSTRAINT fk_project_context_project
        FOREIGN KEY (project_id)
        REFERENCES project(id)
);
```

字段分组说明（V1\.3\.1）：

```Plain Text
稳定信息   goal / key_people / key_links
           半年才改一次，不需要提醒维护

动态状态   focus / blocker / next_action / progress_note
           会随项目推进变化，需要保鲜提示

改名       current_progress → progress_note
           它是一句话的主观判断，不是进度百分比
```

# 七、为什么 Project Context 单独建表？

因为：

```Plain Text
Project
```

描述的是：

> 这个项目是什么。
> 
> 

而：

```Plain Text
Project Context
```

描述：

> 这个项目现在怎么样。
> 
> 

例如：

```Plain Text
项目：
XX项管系统

目标：
完成工单中心一期上线

当前重点：
客服工单分配能力

阻塞：
等待主数据中心提供组织接口

下一步：
周三再次跟进主数据团队

关键人员：
张三 / 李四 / XX厂商
```

如果全部塞进 `project`：

```Plain Text
project.description
project.current_focus
project.blocker
project.next_action
```

最终会变成一个巨大的“备注表”。

单独建 Context 更合理。

# 八、item 表

这是 MVP 最核心的表。

```SQL
CREATE TABLE item (
    id                  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

    project_id          BIGINT,

    title               VARCHAR(500) NOT NULL,

    description         TEXT,

    item_type           VARCHAR(30) NOT NULL,

    status              VARCHAR(30) NOT NULL DEFAULT 'INBOX',

    priority            VARCHAR(10) NOT NULL DEFAULT 'P2',

    planned_date        DATE,

    plan_rank           INTEGER,

    due_at              TIMESTAMPTZ,

    next_follow_up_at   TIMESTAMPTZ,

    waiting_since       TIMESTAMPTZ,

    waiting_expected_at TIMESTAMPTZ,

    completed_at        TIMESTAMPTZ,

    cancelled_at        TIMESTAMPTZ,

    waiting_for         VARCHAR(200),

    related_person      VARCHAR(200),

    created_at          TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    updated_at          TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    version             INTEGER NOT NULL DEFAULT 0,

    CONSTRAINT fk_item_project
        FOREIGN KEY (project_id)
        REFERENCES project(id)
);
```

字段删减（V1\.3\.5）：

```Plain Text
删除 related_company
  它没有任何产品角色

删除 source
  MVP 明确不做第三方集成，IMPORT 没有来源
  将来接 Jira / Git / AI 时再加 source_type + source_id

"人"只保留 related_person 一个自由文本字段
  不进实体、不做枚举、不做"按人员筛选"
  进入 Waiting 时默认带成 waiting_for，用户不用填两遍
```

# 九、Item Type

```Plain Text
TASK
NOTE
```

```Plain Text
TASK       我要做的事（默认）
NOTE       只记录，不进入执行流（只允许 INBOX / DONE / CANCELLED）
```

说明（V1\.3\.1）：

```Plain Text
FOLLOW_UP 是能力（next_follow_up_at 非空），不是类型
WAITING  是状态（status），不是类型
REMINDER 是独立提醒对象（reminder），不是类型
SYNC     本质是带时间的 TASK，用 due_at 表达
```

## TASK

普通工作事项。

例如：

```Plain Text
完成工单分配接口
```

---

跟进（Follow-up）不是类型，而是能力：

```Plain Text
TASK
  + next_follow_up_at = 2026-09-25 10:00
        ↓
它就是一条"跟进事项"
```

为什么把 Follow-up 从类型降为能力（V1\.3\.1）：

```Plain Text
用户记事时不会想"这是 Task 还是 Follow-up"
他只会想"我得催一下张三"

而"我在跟进什么"这个视图
  可以由 next_follow_up_at 非空 100% 推导
  比类型更可靠：用户可能忘选类型，但不会忘设跟进时间

它和 Waiting 的关系
  两者正交，可以同时成立：
    status = WAITING
    waiting_for = 厂商A
    next_follow_up_at = 9/25 10:00
```

跟进动作（V1\.3\.1）：

```Plain Text
到点后点"现在跟进"，只有两种结果

A：我催了，但对方还没回
  记一条 WorkLog
  next_follow_up_at 推到下次
  status 保持 WAITING

B：对方给了
  记一条 WorkLog
  status WAITING → DOING 或 DONE
  清空 waiting_*
```

承诺式文案的推导（V1\.3\.1，不新增字段）：

```Plain Text
我欠别人  related_person 非空 + status IN (TODO, DOING) + due 临近
          → "你答应 {related_person} 在 {due_at} 前 {title}"

别人欠我  status = WAITING + waiting_for 非空 + follow_up 到点
          → "该催 {waiting_for} 了：{title}"
```

能力矩阵（V1\.3\.1）：

| 类型 | 可 WAITING | 可 DONE | 进 Today | 可挂 Reminder | 进日报 |
|---|---|---|---|---|---|
| TASK | 是 | 是 | 是 | 是 | 是 |
| NOTE | 否 | 是（=归档） | 否 | 否 | 否 |

NOTE 的边界（V1\.3\.1 钉死）：

```Plain Text
NOTE 是"事项级记录"，不是知识库文档

允许：
  厂商反馈接口将在下周开放
  环境地址变更说明

不允许（应去别处）：
  技术方案全文
  会议纪要全文
  项目文档
```

---

## NOTE

临时记录。

例如：

```Plain Text
厂商反馈接口将在下周开放
```

# 十、Item Status

```Plain Text
INBOX
TODO
DOING
WAITING
DONE
CANCELLED
```

状态转换：

```Plain Text
INBOX      → TODO, CANCELLED
TODO       → DOING, WAITING, DONE, CANCELLED
DOING      → TODO, WAITING, DONE, CANCELLED
WAITING    → TODO, DOING, DONE, CANCELLED
DONE       → TODO
CANCELLED  → TODO
```

说明：

```Plain Text
DONE → TODO        撤销完成 / 重开（个人工具必须可撤销）
CANCELLED → TODO   恢复误取消
```

# 十一、Inbox 不是 Item Type

这一点非常重要。

不要设计：

```Plain Text
item_type = INBOX
```

Inbox 是：

> 尚未完成整理的 Item 状态。
> 
> 

因此：

```Plain Text
INBOX
```

实际上是：

```Plain Text
status = INBOX
```

例如：

```Plain Text
“明天问一下老王接口什么时候好”
```

刚记录：

```Plain Text
status = INBOX
project_id = NULL
```

整理之后：

```Plain Text
type = TASK
status = TODO
project = XX项目
next_follow_up_at = tomorrow   ← 有跟进能力
```

# 十二、Waiting 的特殊设计

Waiting 是 WorkOS 非常重要的能力。

例如：

```Plain Text
等待：
XX厂商提供接口文档

waiting_for：
XX厂商-张三

next_follow_up_at：
2026-09-25 10:00
```

这样系统可以自动告诉用户：

```Plain Text
⚠️ 有 3 个事项等待超过 3 天
```

而不是让 Waiting 成为一个单纯的状态。

退出 Waiting 时的字段处理（V1\.3\.1）：

```Plain Text
status 从 WAITING 变为 TODO / DOING / DONE
        ↓
清空 waiting_for / waiting_since / waiting_expected_at
        ↓
写一条 Activity
  activity_type = WAITING_ENDED
  remark        = "已等待 3 天"
```

为什么必须这样：

```Plain Text
只保留不清空
  → 下次进入 WAITING 时 waiting_since 是旧的
    会算出"已等待 12 天"这种错误数字

只清空不记录
  → 丢掉"上次等了多久"
    而它是复盘"为什么这个项目慢"的关键证据
```

进入 Waiting 时的轻提示：

```Plain Text
"要不要写一句现在做到哪了？"

因为模型里没有 Item 级进度字段，
"做到一半"的事实只能靠 WorkLog 留下。
```

```Plain Text

WorkLog
```

# 二十、Reminder

```SQL
CREATE TABLE reminder (
    id                  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

    kind                VARCHAR(20) NOT NULL DEFAULT 'ITEM',

    item_id             BIGINT,

    title               VARCHAR(500) NOT NULL,

    remind_at           TIMESTAMPTZ NOT NULL,

    status              VARCHAR(20) NOT NULL DEFAULT 'PENDING',

    triggered_at        TIMESTAMPTZ,

    acknowledged_at     TIMESTAMPTZ,

    created_at           TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_reminder_item
        FOREIGN KEY(item_id)
        REFERENCES item(id)
);
```

状态：

```Plain Text
PENDING      待处理
DISMISSED    用户已处理
CANCELLED    已取消
```

状态机（V1\.3\.1）：

```Plain Text
PENDING → DISMISSED
PENDING → CANCELLED
```

为什么去掉 FIRED：

```Plain Text
服务器触发 ≠ 通知送达 ≠ 用户看到 ≠ 用户处理

用一个状态去承载"送达"是自欺
而 MVP 本来就不承诺送达

所以只建模"待处理 / 已处理 / 已取消"
```

kind：

```Plain Text
ITEM        事项提醒
DAILY       日报提醒
STANDALONE  独立提醒
```

启动补偿（V1\.3\.1）：

```Plain Text
应该提醒 = PENDING 且 remind_at <= now

打开 App 时把这一批列出来即可
不需要判断"用户到底看没看到"
```

为什么启动补偿仍然成立：

```Plain Text
App 没开 → 提醒一直是 PENDING
打开后 → 它自然出现在"待处理提醒"里

不需要"已触发但未送达"这个中间状态
```

# 三十二、Today 排序规则

Today 使用 6 个互斥分区，"归属优先级即分区顺序"，
一条事项只落入第一个命中的分区。

```Plain Text
① 今日计划   planned_date = 今天
② 逾期       due_at < 今天起始 AND status IN (TODO, DOING)
③ 今日到期   due_at 在今天 AND status NOT IN (DONE, CANCELLED, WAITING)
④ 待跟进     next_follow_up_at <= now
⑤ 等待中     status = WAITING 且未到跟进时间
⑥ 待安排     未计划 + 未完成 + 非 WAITING
              且 priority IN (P0, P1)
              上限 5 条
```

分区内部排序：

```Plain Text
今日计划    plan_rank ASC
逾期        due_at ASC
今日到期    priority ASC, due_at ASC
待跟进      next_follow_up_at ASC
等待中      next_follow_up_at ASC NULLS LAST
待安排      priority ASC, due_at ASC NULLS LAST, updated_at DESC
```

关键规则：

```Plain Text
逾期只统计 TODO / DOING
  → 已在别人手里的事项用"待跟进"表达，不用"逾期"

今日计划优先级最高
  → 用户显式选择 > 系统推断

待安排有上限
  → 避免首页变成瀑布

P0 / P1 都无条件进入待安排（V1.3.1）
  → P0 = 用户显式标"紧急"，P1 = 用户显式标"高"
  → 入选只看显式标记
     "due 临近 / 最近有活动"这类推断只用于排序或删除

  为什么修正
    旧规则写成"P0 或 P1 且 due 临近 …"
    结果一条"P1 + 无日期"的事项任何条件都不满足
    在 Today 上完全消失，只能去 Items 里翻
```

界面上归成三块（V1\.3\.5）：

```Plain Text
今天做什么          → ① 今日计划
今天别忘了          → ② 逾期 ③ 今日到期 ④ 待跟进
我在等谁 / 还没安排  → ⑤ 等待中 + ⑥ 待安排

"等待中"不并入第二块：
  对 PM / 产品这类用户，"我在等谁、等了几天"是每天必看，
  也是本产品相对普通待办的头号差异点
```

⑥ 待安排是"决策队列"，不是列表（V1\.3\.5）：

```Plain Text
每条待安排事项直接给三个动作

[今天做]     → planned_date = 今天，进 ① 今日计划
[排到明天]   → planned_date = 明天
[暂不安排]   → priority 显式降为 P2

为什么
  用户有 6 条 P1 未安排时，只看到"待安排 6"
  仍然不知道该做哪个——必须让"看"直接变成"决定"

为什么"暂不安排"是降优先级而不是隐藏
  隐藏 N 天 = 又一条系统推断规则，用户还会怀疑丢数据
  降为 P2   = 用户看得见后果，符合"显式优先于推断"
```

统计层与展示层分离（V1\.2）：

```Plain Text
统计层（后端）
  分区互斥，一条事项只归属一个主分区
  简报数字可直接相加
  → 不需要新增接口字段

展示层（前端）
  允许叠加"次级状态标签"，最多 2 个
  由已有字段推导：
    今日计划 / 逾期 N 天 / 今天到期 / 跟进 HH:mm
    / 等待 XX / 对方逾期 N 天

  取值优先级（最多 2 个）
    等待 XX > 跟进 > 对方逾期 > 逾期 > 今天到期 > 今日计划
```

说明：

> 一条"P0 + WAITING + 今天要跟进"的事项，
> 主分区是"今日计划"，但仍然显示"等待 XX厂商 · 跟进 10:00"。
> 否则会丢掉 WorkOS 最关键的上下文。

等待的"对方逾期"判定（V1\.2）：

```Plain Text
status = WAITING
AND waiting_expected_at IS NOT NULL
AND waiting_expected_at < now
        ↓
标记：对方逾期 N 天

不改变分区归属，只打标记 + 进简报的"需要你决定"
```

```Plain Text
  只给"每条都要决定"的出口，用户就会直接放弃
  "整理"的本质是决定"它是不是一件要做的事"，
  不是"它属于哪个项目"
```

```Plain Text

设置优先级

```

例如：


# 五十、Reminder

MVP **取消后端调度**（V1\.3\.5）：

```Plain Text
MVP 没有外部推送渠道（不做邮件 / 短信 / IM）
  后端扫描并"触发"提醒，不会真正通知到任何人
  → 那这次扫描没有意义，还多一个后台调度器

改由客户端驱动
  打开 App      → 查询 PENDING 且已到期，展示（这就是启动补偿）
  前台运行时     → 每 30~60 秒查一次
  Tauri 装好后   → 本地通知由客户端调度
```

查询：

```SQL
SELECT *
FROM reminder
WHERE status = 'PENDING'
  AND remind_at <= NOW()
ORDER BY remind_at
LIMIT 100;
```

展示（不再改状态）：

```Plain Text
到期 → 展示给用户
提醒本身的状态只在"用户处理这次提醒"时才变
```

用户处理这次提醒：

```Plain Text
status = DISMISSED
acknowledged_at = now()
```

三个动作（V1\.3\.5）：

| 动作 | 对 Reminder | 对业务事实（Item） |
|---|---|---|
| 现在跟进 | → 已处理 | 记一条工作记录；更新下次跟进时间或改状态 |
| 稍后提醒 | 修改 `remind_at` | **不变** |
| 忽略这次 | → 已处理 | **不变**（`next_follow_up_at` 保持原值） |

设计意图：

```Plain Text
用户点"关闭提醒"≠"我已经催了张三"
可能只是"我现在不想看它"

如果混在一起：
  提醒关掉 → 系统以为催过了 → 下次不再提醒 → 事情真的漏了

所以：提醒是注意力机制，不是业务状态
```

说明（V1\.3\.1）：

```Plain Text
不再有 FIRED
  服务器触发 ≠ 通知送达 ≠ 用户看到 ≠ 用户处理
  MVP 不承诺送达，所以不建模它

启动补偿
  打开 App 时查：PENDING 且 remind_at <= now
  这一批就是"待处理提醒"
```

# 五十六、状态转换定义

```Java
Map<ItemStatus, Set<ItemStatus>> TRANSITIONS = Map.of(
    INBOX, Set.of(TODO, CANCELLED),
    TODO, Set.of(DOING, WAITING, DONE, CANCELLED),
    DOING, Set.of(TODO, WAITING, DONE, CANCELLED),
```

```Plain Text

```

# 七十四、第一版验收标准

## 快速记录

必须做到：


## Today

必须自动显示：

```Plain Text

① 今日计划
② 逾期
③ 今日到期
④ 待跟进
⑤ 等待中
⑥ 待安排（priority IN (P0,P1)，上限 5 条）
```



