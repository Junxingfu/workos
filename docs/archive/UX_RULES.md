# WorkOS UX Rules

> 本文件定义 WorkOS 的交互规则。
>
> DESIGN.md 解决“长什么样”。
>
> 本文件解决“应该怎么用”。

---

# 1. 核心 UX 原则

WorkOS 的核心 UX 目标：

> **让用户少想、少填、少维护，但始终知道系统为什么这样展示。**

---

# 2. 三秒原则

用户进入一个页面后：

### 3 秒

知道：

```text
我在哪里？
```

### 10 秒

知道：

```text
我应该关注什么？
```

### 30 秒

知道：

```text
我今天应该做什么？
```

---

# 3. 上下文恢复原则

WorkOS 的核心竞争力不是：

> 管理更多任务。

而是：

> **更快恢复被打断之前的工作上下文。**

因此任何页面都应该帮助用户回答：

```text
我上次做到哪里？
为什么做到这里？
下一步是什么？
有没有人在等我？
我是不是在等别人？
```

---

# 4. 不让用户重复输入事实

核心规则：

> **能从已有事实推导出来，就不要让用户再次输入。**

例如：

已经完成 Item：

```text
不要强制 WorkLog
```

已经有：

```text
nextFollowUpAt
```

不要强制再次创建同时间 Reminder。

已经完成：

```text
Item
```

Daily 可以直接使用它。

---

# 5. Quick Capture

Quick Capture 必须：

```text
< 5 秒
```

理想：

```text
输入标题
↓
Enter
↓
Inbox
```

不要要求：

```text
项目
优先级
日期
状态
负责人
标签
```

---

# 6. Inbox

Inbox 的心理模型：

> **我还没有决定怎么处理这件事。**

不要把 Inbox 做成：

> “任务列表”。

---

# 7. Inbox 与“还没安排”的区别

必须通过 UI 文案直接解释：

### Inbox

> 这件事我还没决定怎么处理。

### 还没安排

> 我已经承认这是一件正式的工作，但还没决定什么时候做。

这是两个不同心理状态。

---

# 8. Inbox 不允许成为黑洞

如果 Inbox 数量增加：

不要：

```text
继续要求用户逐条整理
```

必须提供：

```text
整理最老的一条
```

和：

```text
先都收下
```

---

# 9. “先都收下”

语义：

```text
status = TODO
priority = P2
project = null
```

不要偷偷：

```text
自动分项目
自动定日期
自动设优先级
自动推荐
```

---

# 10. Today

Today 是：

> **决策面**

不是：

> 全部重要事项的过滤结果。

---

# 11. Today 的入选必须可解释

Today 中每一条事项：

用户应该能够回答：

> **“为什么它出现在这里？”**

例如：

```text
今日计划
```

因为用户显式安排。

或者：

```text
逾期
```

因为 dueAt 已经过期。

或者：

```text
今日到期
```

因为 dueAt 在今天。

或者：

```text
待跟进
```

因为 nextFollowUpAt 到期。

或者：

```text
等待中
```

因为状态为 WAITING。

或者：

```text
还没安排
```

因为符合后端定义的捕漏规则。

---

# 12. Today 不使用黑箱推荐

MVP 禁止：

```text
AI 推荐你今天做这个
```

也禁止：

```text
根据最近打开次数
根据用户行为
根据“感觉重要”
```

决定 Item 是否进入 Today。

排序可以优化。

入选必须基于明确事实。

---

# 13. Today 排序

排序可以由后端完成。

前端：

> 不重新排序。

如果后端已经提供排序：

```text
直接展示。
```

---

# 14. Today 的视觉优先级

顺序固定：

```text
今天做什么
↓
今天别忘了
↓
我在等谁 / 还没安排
```

不要把：

```text
Waiting
```

做得比：

```text
Today Plan
```

更突出。

---

# 15. Today Plan

默认突出：

```text
3 件
```

不是硬限制。

如果后端返回更多：

可以显示：

```text
3 / 7
```

但视觉上重点仍然是用户当前选定的计划。

---

# 16. Overdue

逾期必须明显。

但不要：

```text
整张卡红色
```

推荐：

```text
红色 icon
+
红色 metadata
```

---

# 17. Waiting

Waiting 不只是：

```text
status = WAITING
```

用户真正关心：

```text
谁
+
什么
+
预计什么时候
+
什么时候我要再次推动
```

所以 Waiting UI 应该突出：

```text
waitingFor
waitingExpectedAt
nextFollowUpAt
```

---

# 18. Follow-up

Follow-up 不是一种 Item。

不要出现：

```text
Type = FOLLOW_UP
```

用户看到：

```text
跟进
```

即可。

---

# 19. Waiting + Follow-up 可以同时存在

例如：

```text
等待厂商接口文档

等待对象：
厂商A

预计：
今天

下一次跟进：
明天 10:00
```

这完全合理。

---

# 20. Project

项目详情必须帮助用户：

> **10 秒恢复上下文。**

第一屏必须出现：

```text
当前重点
当前阻塞
下一步
```

---

# 21. Project 不要变成第二个 Jira

不要在 Project Detail 首页放：

```text
复杂 Kanban
Sprint
Burn-down
Story Point
Velocity
大量统计
```

这些不属于 MVP 核心。

---

# 22. Item

Item 是：

> 一个需要进入用户注意力系统并最终闭环的事项。

不是：

```text
一个技术步骤
```

也不是：

```text
一个数据库记录
```

---

# 23. Item 操作原则

用户打开 Item 后：

```text
看事实
↓
做动作
```

而不是：

```text
查看 20 个字段
↓
找到按钮
↓
进入第二页面
↓
继续操作
```

---

# 24. 状态变化

状态操作必须来自：

```text
allowedTransitions
```

用户看到：

```text
开始处理
等待别人
完成
取消
```

而不是：

```text
INBOX
TODO
DOING
WAITING
DONE
CANCELLED
```

技术枚举可以在开发工具里存在。

用户界面应该使用用户语言。

---

# 25. 删除

删除不是主要动作。

优先使用：

```text
取消
归档
```

而不是：

```text
Delete
```

如果存在删除操作：

必须二次确认。

---

# 26. 表单原则

表单字段：

> **只放当前动作所需要的字段。**

例如进入 Waiting：

只问：

```text
在等谁 *
预计时间
下一次跟进
```

不要打开一个完整 Item Edit Form。

---

# 27. Drawer 优先于跳转

Item 操作：

```text
列表
 ↓
Drawer
```

只有需要：

```text
完整编辑
```

才考虑进入完整页面。

---

# 28. 操作成功后的行为

默认：

```text
保存成功
↓
刷新事实
↓
保持用户上下文
```

不要无意义地：

```text
跳转首页
关闭整个页面
跳到项目页
```

---

# 29. 键盘

快捷键是加速器。

不是：

> 用户必须学习的一门语言。

任何快捷操作必须存在鼠标等价入口。

---

# 30. Command Palette

如果未来实现：

```text
⌘K
```

它应该用于：

```text
搜索
快速进入页面
快速创建
快速执行明确动作
```

不要把所有功能都塞进去。

---

# 31. Empty State

Empty State 必须解释：

```text
为什么为空
```

必要时：

```text
下一步是什么
```

例如：

```text
今天还没有计划事项

从“还没安排”中选择今天要做的工作。
```

---

# 32. Loading

页面加载：

```text
Skeleton
```

局部操作：

```text
Button loading
```

不要整个页面闪烁。

---

# 33. Error

错误消息应该：

```text
事实 + 下一步
```

例如：

```text
保存失败，请重试。
```

---

# 34. 防止误操作

高风险操作：

```text
删除
取消
覆盖日报
```

必须有明确确认。

普通操作：

```text
状态切换
计划
跟进
```

尽量不增加确认弹窗。

---

# 35. 用户中断原则

WorkOS 用户经常被打断。

所以：

> **任何 Drawer / Modal / 表单都不能让用户忘记自己刚才在做什么。**

例如关闭 Drawer：

不应该丢失未保存输入。

如果有修改：

提示：

```text
有未保存修改，确定关闭？
```

---

# 36. 加班场景

不要因为晚上 23:00 就自动改变 UI。

不要：

```text
Good night
辛苦了
该休息了
```

WorkOS 是工作工具。

时间只是事实。

---

# 37. 不做拟人化

禁止：

```text
嘿！准备好开始高效的一天了吗？
🎉 今天也要加油！
```

WorkOS 应该：

```text
今天 · 9月25日
```

克制、直接。

---

# 38. 不做 AI 味文案

禁止：

```text
✨ Smart Insights
🚀 Boost your productivity
🧠 AI-powered workflow
```

MVP 没有 AI，就不要模拟 AI。

---

# 39. 页面切换

路由切换应该：

```text
快
稳定
不产生无意义动画
```

---

# 40. 最终 UX 判断

每一个新增 UI 都问：

```text
这个 UI 帮助用户完成什么任务？
```

如果回答不清楚：

> 删除它。
