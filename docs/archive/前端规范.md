# WorkOS 前端规范

> 产品版本：MVP / PRD V1.3.5
> 技术栈：Vue 3 + TypeScript + Vite + Vue Router + Ant Design Vue
> 适用范围：`workos-web/`
> 路径约定：文中 `src/...` 均相对 `workos-web/`
> 文档版本：v2.0（工作界面重构规范）

**这是 WorkOS 前端的唯一规范文件。**

它不是产品需求文档，也不是单纯的视觉规范，而是**可直接执行的前端重构规范**：页面构成、信息层级、组件行为、视觉系统、交互反馈都在这里。

给 Agent 执行用的规则化形态是同目录的 `前端Agent规则.md`（硬约束编号 + 契约 + 可直接跑的验收命令）。两份同源：本文件回答「是什么、为什么」，那份回答「照着做、怎么验」。**冲突时以本文件为准**，并顺手修正那一份。

冲突优先级：

```text
产品需求（PRD）
  > 本文件
  > 既有实现
  > Agent 自由发挥
```

# 1. 目标与产品定位

WorkOS 是：

> **一个帮助用户快速恢复工作上下文、明确当前行动、处理等待事项、记录工作过程的个人工作驾驶舱。**

不是：企业后台管理系统 / Jira / Trello / Notion / Todoist / 数据 Dashboard / KPI 看板 / CRUD 管理平台。

用户打开后第一反应应该是：

```text
我现在应该做什么？
```

而不是：

```text
这里有多少任务、多少项目、多少状态？
```

**本次重构不做的事**：不增加业务能力，不改变后端 API、产品模型、路由、状态机。

# 2. 设计原则与优先级

## 2.1 问题定义

WorkOS 的界面问题不是「不好看」，而是：

```text
信息层级不够明显
  → 页面像 CRUD 后台
  → 所有内容都一样重要
  → 用户需要阅读才能理解页面
  → 交互路径过长
  → 工作过程中频繁打开 Drawer
  → 页面「看起来有东西」，但不知道下一步做什么
```

## 2.2 优先顺序

发生取舍时按这个顺序，靠前的永远赢：

```text
信息架构 > 页面布局 > 内容密度 > 操作路径 > 状态表达 > 视觉层级 > 动画 > 装饰
```

三条硬判断：

- 视觉效果与信息清晰度冲突 → 优先信息清晰度
- 动画与操作效率冲突 → 优先操作效率
- 设计让页面更漂亮但增加操作步骤 → 不采用

不确定时：**Card 还是 List → 选 List；要不要打开 Drawer → 优先行内动作；要不要加一个视觉效果 → 不加。**

## 2.3 三个最关键的结构性决定

```text
1. ItemCard → ItemRow：从「卡片事项」变成高密度工作列表
2. Drawer = 深度编辑，不是所有操作的入口：完成/开始/等待/跟进/安排直接在行内完成
3. 今天 = 工作驾驶舱：左栏回答「现在做什么」，右栏回答「还有什么上下文不能忘」
```

# 3. 视觉系统

## 3.1 关键词

```text
Calm / Dense / Focused / Editorial / Work-oriented / Low decoration
安静 / 紧凑 / 聚焦 / 有秩序 / 有工作感
```

不要：科技感、炫酷、玻璃、渐变、大圆角、卡片堆叠、Dashboard、营销页。

## 3.2 颜色

主色（只用于 Primary Button、Active 导航、Selected、Focus、少量关键强调、链接）：

```css
--color-primary: #4f46e5;
--color-primary-hover: #4338ca;
--color-primary-light: #eef2ff;
```

基础色：

```css
--color-text: #1f2329;
--color-text-secondary: #646a73;
--color-text-tertiary: #8f959e;
--color-border: #e5e6eb;
--color-border-light: #f0f1f3;
--color-bg: #f7f8fa;
--color-surface: #ffffff;
--color-hover: #f5f7fa;
```

语义色（表达状态，不负责装饰）：

```css
--color-success: #16a34a;
--color-warning: #d97706;
--color-danger: #dc2626;
--color-info: #2563eb;
```

配比目标：中性 80% / 主色 10% / 语义色 10%。禁止大面积使用主色。

**颜色必须接进 Ant Design 主题**（`a-config-provider` 的 `token.colorPrimary`），否则 antd 组件仍是默认蓝。

## 3.3 字号

```text
页面标题    24px / 28px / 600
区块标题    15px / 22px / 600
事项标题    14px / 20px / 500
正文        14px / 22px / 400
元信息      12px / 18px / 400
```

系统字体，不引入 Web Font。不要大量使用 11px 中文。

## 3.4 圆角

```text
按钮 / 输入框   6px
Popover        8px
Drawer / Modal 10px
事项行          0px   ← 不做圆角卡片
区块 / 页面     0px
```

## 3.5 阴影

阴影只表示「脱离文档流」，只允许：

```text
Drawer / Modal / Popover / Dropdown
```

唯一例外：事项行选中态用 `inset 2px 0 0` 画左侧色条（不是 elevation）。

普通事项行、区块、Sidebar、页面头部、普通按钮都不允许有阴影。hover 只改背景色。

## 3.6 密度与间距

4px 基础栅格，纵向节奏：

```text
页面间距 / 区块间距      32px / 28px
区块标题到内容          12px
事项行纵向内边距        10px
元信息间距              4~8px
```

事项行高度：

```text
默认 60px 左右 · 紧凑 52px · 复杂（两行）68px
```

不允许默认 88px / 100px 这种「为了呼吸感把内容撑大」的做法。

# 4. 布局

## 4.1 App Shell

```text
┌──────────────────────────────────────────────┐
│ Sidebar 208px │ Main                        │
│               │   Page Header               │
│               │   Content（max 1200px 居中）│
└──────────────────────────────────────────────┘
```

内容区最大 1200px，不无限拉伸。1080px 宽度下不允许横向滚动。

## 4.2 Sidebar

一级导航只有五项，顺序固定：

```text
今天 / 收件箱 / 全部事项 / 项目 / 日报
```

规则：

- Sidebar 是导航，不是视觉主体，必须安静
- Active 用「左侧 2px 主色条 + 极浅主色底 + 文字加粗」，不用彩色 Pill
- 不使用巨大 Logo、不堆统计数字、不放复杂树、不放二级菜单
- 只有「收件箱」显示数量（唯一有行动价值的数字）

## 4.3 页面背景

```text
灰色页面背景 → 白色工作区域 → 列表 / 内容
```

不要：灰色背景 + 一层层白色 Card 堆叠。

## 4.4 页面 Header

```text
标题 / 副标题（日期、数量、状态）/ 最多 1 个主要操作
```

例如今天页：`今天` + `9月26日 · 星期六` + `[继续上次]`。

禁止：`标题 + [刷新][导出][新增][筛选][更多][设置]`。操作要靠近它影响的对象。

## 4.5 区块与列表

```text
区块标题                          计数
──────────────────────────────────────
○  事项标题            项目   今天   P1
   等待张三 · 预计 09/27
```

- 区块不是卡片：只有标题行和一条分隔线
- 列表是白色工作区，行与行之间用 1px 细线
- 不使用 uppercase 英文 micro label，中文产品不模仿英文 SaaS 套路

# 5. ItemRow（系统里最重要的组件）

`src/components/ItemCard.vue`（文件名保留，语义是 Row）。

展示组件，**不推导业务规则**：能出现哪些动作完全由后端 `allowedTransitions` 决定；是否逾期、今天/明天只做展示。

## 5.1 结构

```text
第一行：[状态符号] [标题]                [项目] [日期] [优先级] [行内动作]
第二行：最多两条有价值的事实（等待 / 跟进 / 逾期 / 剩余步数）
第三行（可选）：页面注入的扩展区（如收件箱的整理面板）
```

约束：

- 默认最多两行
- 长标题单行省略号截断，不换行、不破坏行高
- 行高落在 52~68px 区间
- 行内动作常驻 DOM，默认 `opacity: 0`，hover / 键盘聚焦 / 选中时出现，**不改变行高**

## 5.2 状态符号

```text
○ 待办 / 待整理      ◐ 进行中      ◷ 等待中      ✓ 已完成      × 已取消
```

- 符号表达状态，颜色只是辅助
- 符号必须有 `aria-label` 与 `title`（用户语言：待办 / 进行中 / 等待中 / 已完成 / 已取消）
- 界面文案不出现 `INBOX / TODO / DOING / WAITING / CANCELLED`

## 5.3 优先级

```text
● P0（Danger）· ● P1（Warning）· P2 / P3 弱化，不加圆点
```

不把优先级做成彩色 Badge。

## 5.4 元信息

一个事项最多：1 个状态 + 1 个优先级 + 1 个日期 + 1 个项目 + 1 个特殊状态。第二行最多两条，其余进 Drawer。

## 5.5 状态样式

```text
默认    透明
Hover   background: #f5f7fa
Selected background: #eef2ff + 左侧 2px 主色条
Focus   outline: 2px solid rgba(79,70,229,.25)
已完成/已取消  标题降为三级文字
```

## 5.6 行内动作

高频动作必须在行内完成，不为改一个状态打开 Drawer：

| 动作 | 出现条件 |
|---|---|
| 完成 | `allowedTransitions` 含 `DONE` |
| 开始 / 恢复 | 含 `DOING`（等待中显示「恢复」） |
| 重新打开 | 已完成且含 `TODO` |
| 等待 | 含 `WAITING`（点了直接落到「在等别人」表单） |
| 跟进 | 到点跟进或等待中（点了直接落到跟进表单） |
| 安排今天 | 页面传 `decisionMode`（今天的「还没安排」） |

提交中只让被点的控件转圈，其他按钮禁用，避免重复提交。

# 6. ItemDrawer

Drawer 的定位是：

> **事项深度编辑 + 完整上下文查看，不是所有操作的入口。**

## 6.1 尺寸与头部

```text
宽度 520~560px（当前 540px）
头部：事项标题 + 「项目 · 优先级 · 状态」
```

禁止在抽屉顶部用一条彩色状态条表示状态。

## 6.2 分区顺序

```text
标题（可编辑）
事实行：项目 / 优先级 / 计划日期
等待与跟进：在等别人 / 设下次跟进 / 取消（二次确认）
描述 / 清单
我在等谁（仅等待中）
到点跟进（仅到点或等待中）
记一句 + 已记录
历史（折叠）
删除（仅待整理，最低视觉权重，二次确认）
```

不显示 `ID / createdAt / version / source`。

## 6.3 底部主要动作

固定吸底，随状态变化，用户打开就知道下一步是什么：

```text
待办    → 完成事项
进行中  → 完成事项
等待中  → 恢复处理
已完成  → 重新打开
```

「编辑 / 保存」不是用户真正想做的主要动作。

## 6.4 行为约束

- 属性即时保存；标题、描述失焦保存；保存中禁用状态按钮，避免抢 `version`
- 刷新事实时**不得覆盖用户正在编辑的文本**
- 关闭 Drawer 不得丢失未保存输入
- 主要动作不得先改本地状态再等服务器

# 7. 页面规格

## 7.1 今天 `/today`

**目标**：打开后 3 秒内知道今天要做什么。

```text
今天                                    9月26日 · 星期六        [继续上次]

┌────────────────────────────────┬──────────────────┐
│ 今日计划                2 / 3   │ 等待中        2  │
│ ○ …                            │ 张三 · 接口确认   │
│ ○ …                            │ 明天跟进          │
│                                │ ───────────────  │
│ 今天别忘了     1 逾期/0 到期/0  │ 最近工作          │
│   逾期 / 今日到期 / 待跟进      │ 09:40 完成工单…   │
│                                │                  │
│ 还没安排               最多 5 条 │                  │
│ ○ …                    [安排今天]│                  │
└────────────────────────────────┴──────────────────┘
```

- 左主区负责「现在要做什么」，宽度约 820px；右栏负责「还有什么上下文不能忘」，约 300px
- 右栏只放**等待中**与**最近工作**，不放 KPI、不放「今日完成 12 / 进行中 5」
- 「继续上次」= 回到最近记过工作的事项
- 左主区顺序固定：今日计划 → 今天别忘了（逾期 → 今日到期 → 待跟进）→ 还没安排
- 每条都要能解释为什么入选；排序由后端给，前端不重排
- 逾期用 Danger 文字/符号，不整行变红
- 「安排今天」直接在行内完成

## 7.2 收件箱 `/inbox`

**定位**：刚刚捕获、还没有完成澄清的工作队列。

```text
收件箱                                    3 个待处理
记录一个新的事情…                          Enter ↵
[先都收下]
○ 供应商反馈接口问题              10:32    整理
○ 客服反馈一个 bug                09:45    整理
```

- 快速记录只要标题，Enter 创建，不要求项目 / 优先级 / 日期 / 状态
- 点行内「整理」原位展开，**只允许**：项目、优先级、收下、不做、打开详情
- 「收下」= 转 TODO（承认它是正式工作），之后由「还没安排」决定什么时候做
- 「不做」= 转已取消，必须二次确认
- 「先都收下」= 批量转 TODO，**不得**自动填项目 / 优先级 / 日期
- **排期不放进收件箱**：那属于「还没安排」
- 语义边界：`收件箱 = 我还没决定怎么处理` ≠ `还没安排 = 已承认是正式工作，只是没定什么时候做`

## 7.3 全部事项 `/items`

```text
全部事项 10            [搜索标题或描述]
[未完成][待办][进行中][等待中][已完成]  [优先级] [项目]
○ 事项 A
○ 事项 B
```

- 默认「未完成」
- 行内可直接完成 / 开始 / 等待 / 跟进
- 禁止 KPI 卡片（`P0 12 / P1 32 / Doing 10` 这类）

## 7.4 项目 `/projects`

列表，不是卡片网格：

```text
项目名称                        进行中
当前：工单分配服务
进行中 3 · 等待 1 · 最近活动 09-26
```

## 7.5 项目详情 `/projects/:id`

**目标**：离开两天后回来，10~30 秒恢复上下文。

```text
项目名称
进行中 · 现状更新于 09-26 03:11 · 0 天前

项目现状
  当前重点 / 当前进展 / 下一步        ← 第一屏
  当前阻塞 / 当前目标
  关键联系人 / 关键链接 / 备注

进行中  N   ← 事项列表，行内可推进
等待中  N

[归档项目]
```

- Context 优先结构化展示，Markdown 备注放最后
- 数字不进第一屏，也不做统计卡片
- 禁止 Kanban / Sprint / Burn-down / Story Point / Velocity / 完成率
- 归档是业务状态，不做物理删除

## 7.6 日报 `/daily`

```text
日报 · 9月26日            [←] [日期] [→]  [按记录生成] [保存]
正文（有未保存修改 / 已与后端一致）
这一天的记录
```

- 生成只产生快照，点「应用」才覆盖正文
- 有未保存修改时，切日期或离开页面必须先确认
- 禁止图表、饼图、完成率卡片、大量统计数字

# 8. 反馈与状态

## 8.1 空态

不要巨大插画。直接说明「为什么为空」，必要时给一个动作：

```text
今天还没有计划事项
从下面「还没安排」里挑一件今天要推进的。
```

## 8.2 加载

```text
很快    → 直接展示（不强行加 300ms Skeleton）
稍慢    → Skeleton，且骨架要模拟真实布局（符号 + 文字条）
首屏    → 允许整块 loading
后续刷新 → 只允许触发点局部 loading，禁止整页变灰
```

按钮 loading 保持原文字 + spinner，不要换成「Loading...」，避免宽度跳动。

## 8.3 错误

告诉用户「发生了什么 + 现在怎么办」，统一走 `fail(error)`：

```text
保存失败，请重试。
```

不要只显示 `Error`。

## 8.4 Toast 与撤销

```text
✓ 已完成   [撤销]
```

- 只有真正适合撤销的操作给撤销：完成、归档、取消、批量变更
- 打开页面、刷新、点击普通事项**不产生 Toast**

## 8.5 动画

```text
Hover 100~120ms · Button 100~150ms · Popover 120~160ms · Drawer 160~200ms · Toast 150~200ms
```

允许：状态变化、Drawer、Popover、Modal、Toast、Hover。
禁止：页面飞入、**列表错峰入场**、大范围 transform、装饰性动画。
必须支持 `prefers-reduced-motion: reduce`。

# 9. 交互规则

## 9.1 三秒 / 十秒 / 三十秒

```text
3 秒    知道我在哪里
10 秒   知道该关注什么
30 秒   知道今天该做什么
```

## 9.2 不让用户重复输入事实

能从已有事实推导出来的，不要再让用户输入。每加一个输入框都要问：「这个信息是否已经能从已有事实得到？」

## 9.3 写操作之后

```text
用户操作 → API → 成功 → 重新 GET → 重新渲染
```

- **不做乐观更新**；失败时恢复原状态并提示，不允许 UI 停在错误的成功态
- 事项离开列表 → 选中态与焦点交给相邻一条，并保持在可视区
- 就地编辑属性 → 选中态留在本行
- 代价高的动作 → 提示里带撤销

## 9.4 状态变更

- 只能 `POST /api/items/{id}/transitions`
- 允许的动作来自后端 `allowedTransitions`，前端不得复制状态机
- 文案用用户语言：开始做 / 在等别人 / 完成 / 取消

## 9.5 危险动作

删除、取消、覆盖日报必须二次确认；状态切换、计划、跟进尽量不加确认弹窗。

删除不是主要动作，优先「取消 / 归档」。

## 9.6 键盘与可访问性

```text
j / k        上下选择
Enter        打开当前项（收件箱里也是创建 Capture）
Esc          关闭 Drawer / Popover，取消选中
↑ / ↓        仅当页面本身不滚动时用于选择（收件箱）
1/2/3/4      收件箱内设优先级
Alt + Space  聚焦快速记录
```

- 快捷键是加速器，**任何快捷操作都必须有鼠标等价入口**
- 所有可交互元素必须有 `:focus-visible`，禁止 `outline: none` 后不补
- icon-only 按钮必须有 `aria-label`
- 状态不能只靠颜色表达

## 9.7 操作路径

```text
主要动作 ≤ 3 次操作；普通编辑 ≤ 3~5 次关键交互
高频动作不要要求打开 Drawer
```

# 10. 工程约定

## 10.1 技术栈固定

```text
Vue 3 / TypeScript / Vite / Vue Router / Pinia / Ant Design Vue / Axios / Dayjs
```

禁止引入 React、Tailwind、Element Plus、其他 CSS 框架、其他状态管理库、图表库。

## 10.2 数据流

```text
页面 → api/index.ts → api/client.ts → Axios
```

禁止在页面组件里直接 `axios.get/post`。

## 10.3 类型与时间

- 后端 ID 是 Long，前端统一 `id: string`，禁止 `parseInt(id)` / `Number(id)`
- 时间：`dayjs(iso)` 展示，`toISOString()` 提交，纯日期 `YYYY-MM-DD`
- 禁止 `iso.substring(...)`，禁止前端自行判断「今天」和日界线

## 10.4 状态管理

MVP 不用 Pinia 保存页面数据。只有真正出现跨页面共享状态时才引入。

## 10.5 复用尺度

```text
重复出现两次      → 先观察
重复出现三次且语义稳定 → 考虑抽组件或组合式函数
```

抽**行为**（如列表动作与位置交接）值得；抽**视觉壳子**（BaseCard / BasePanel）要怀疑。

# 11. Ant Design Vue 的定位

Ant Design 负责：行为、交互、可访问性、基础组件能力。
WorkOS 负责：布局、密度、视觉层级、Item、Section、Page、工作流。

不要让 Ant Design 默认样式等于 WorkOS 设计。必须覆盖：

```text
Button / Input / Select / Drawer / Modal / Dropdown / Tooltip / Tag / Empty / Spin
```

覆盖方式优先级：

```text
1. a-config-provider 的 token（颜色、圆角、字号）—— 主色必须走这里
2. main.css 里的全局覆盖（控件圆角、Drawer 圆角、Popover 圆角）
3. 组件内 scoped 样式（布局与密度）
```

# 12. 绝对禁止

```text
禁止 1   Dashboard 化：KPI 卡片、大数字、统计 Dashboard、图表、完成率
禁止 2   Card 化：每个 Item 一张卡、每个 Section 一张卡、项目/日报一张卡
禁止 3   玻璃拟态：backdrop-filter、glassmorphism
禁止 4   渐变（除非产品明确要求）
禁止 5   大量动画：页面加载动画、列表 stagger、卡片飞入、大范围 transform
禁止 6   为了「年轻」增加装饰：emoji、大插画、彩色背景、浮动装饰、渐变 blob
禁止 7   复制 Linear：可以借鉴信息密度、快捷操作、键盘体验，不能复制视觉皮肤与品牌语言
禁止 8   深色模式（MVP 不做，但 Token 要留好）
禁止 9   前端推导业务规则（是否逾期、为什么进 Today、今天是哪天）
禁止 10  绕过状态机（PUT status）与乐观更新
```

# 14. 交付验收

## 14.1 静态自检（在 `workos-web/` 下执行）

```bash
npx vue-tsc --noEmit     # 不得新增类型错误
npx vite build           # 必须通过
```

改动前已知 2 个历史类型错误（`src/api/client.ts` 拦截器签名、`vite.config.ts` 缺 node 类型）。这个数字只能减少，不能增加。

应输出为空的检查：

```bash
rg -n "axios\." src/pages src/components          # 页面直连 axios
rg -n "linear-gradient|backdrop-filter" src       # 渐变 / 玻璃拟态
rg -n "parseInt\(|Number\([^)]*[Ii]d\b" src       # ID 当数字用
rg -n "box-shadow" src/styles/main.css src/**/*.vue  # 只允许出现在 Drawer/Modal/Popover/Dropdown
```

需要逐条人工确认的检查：

```bash
rg -n "transition\(" src/pages src/components     # 状态变更唯一入口，且带 version
rg -n "updateItem\(" src/pages src/components     # 确认没有传 status
rg -n "'(INBOX|TODO|DOING|WAITING|DONE|CANCELLED)'" src/pages src/components
#  每一处只允许是类型映射表的 key、筛选器定义、与 allowedTransitions 的比较
rg -n "border-radius" src/styles/main.css         # 事项行/区块必须是 0
```

## 14.2 浏览器验收

有机会驱动浏览器时必须真的点一遍：

1. 访问每个路由，收集 `console error / pageerror / HTTP ≥ 400` —— 必须为 0
2. 检查 `1280 × 800`、`1440 × 900`、`1728 × 1117`，以及 100% / 125% / 150% 缩放
3. 检查无横向滚动
4. 主要流程真的点一遍（不改用户数据，用临时数据并清理）
5. 检查：行内动作可用、点击瞬间列表不清空、动作后焦点仍在列表、抽屉输入不被刷新覆盖、关抽屉不丢输入
6. 检查长标题、大量数据、空态、错误态

## 14.3 截图检查清单

```text
视觉：是否仍然像后台？卡片多不多？颜色多不多？阴影多不多？圆角多不多？密度够不够？有没有大面积无意义留白？
信息：第一眼知道页面干什么吗？知道最重要的信息吗？知道下一步动作吗？
交互：高频动作需要打开 Drawer 吗？需要超过 2 次点击吗？hover 出现合理操作吗？focus 清楚吗？loading 稳定吗？
```

## 14.4 提交前必答

```text
1. 我打开页面 3 秒内知道现在应该做什么吗？
2. 我能不能快速扫描 10 个 Item？
3. 完成一个 Item 是否足够快？
4. 我是否必须打开 Drawer 才能完成简单操作？
5. 我离开项目两天后回来，能不能快速恢复上下文？
6. 页面是否有明显的「后台系统感」？
```

## 14.5 判定标准

如果一个页面看起来很精致、有很多阴影、漂亮动画、玻璃效果、大量 Badge，但用户仍然需要：

```text
打开 Drawer → 找状态 → 修改 → 保存 → 关闭
```

那么这个页面**重构失败**。

最终质量目标不是「哇，好炫」，而是：

> **安静、清晰、紧凑、专业；让我更快恢复工作，而不是让我管理这个工具。**

