# WorkOS 前端 UI/UX 重构实施规范 v2.0

> **文档性质：Agent 可直接执行的前端重构规范**
>
> 本文不是产品需求文档，也不是单纯的视觉设计规范。
>
> Agent 必须按照本文完成 WorkOS Web MVP 的页面布局、视觉体系、交互方式和组件重构。
>
> **核心原则：不增加业务能力，不改变后端 API 和产品模型，只重构前端体验。**

---

# 1. 重构目标

## 1.1 产品定位

WorkOS 不是：

* 企业后台管理系统
* Jira
* Trello
* Notion
* Todoist
* 数据 Dashboard
* KPI 看板
* CRUD 管理平台

WorkOS 应该呈现为：

> **一个帮助用户快速恢复工作上下文、明确当前行动、处理等待事项、记录工作过程的个人工作驾驶舱。**

用户打开 WorkOS 后，第一反应应该是：

> “我现在应该做什么？”

而不是：

> “这里有多少任务、多少项目、多少状态？”

---

# 2. 本次重构的核心问题

当前页面不要继续通过以下方式解决“页面不好看”：

* 增加阴影
* 增加圆角
* 增加颜色
* 增加动画
* 增加渐变
* 增加卡片
* 增加玻璃效果
* 增加 Dashboard 卡片
* 增加 KPI
* 增加更多 Badge
* 增加更多图标
* 模仿 Linear 的所有视觉元素

这些不是 WorkOS 当前最核心的问题。

真正需要解决的是：

```text
信息层级不够明显
        ↓
页面像 CRUD 后台
        ↓
所有内容都一样重要
        ↓
用户需要阅读才能理解页面
        ↓
交互路径过长
        ↓
工作过程中频繁打开 Drawer
        ↓
页面“看起来有东西”，但不知道下一步做什么
```

因此本次重构优先级必须是：

```text
信息架构
    >
页面布局
    >
内容密度
    >
操作路径
    >
状态表达
    >
视觉层级
    >
动画
    >
装饰
```

---

# 3. 最重要的设计原则

## 3.1 List First，而不是 Card First

WorkOS 的核心对象是工作事项。

工作事项数量可能很多。

因此：

> **Item 默认必须表现为“工作列表行”，而不是 Card。**

禁止：

```text
┌──────────────┐
│ 任务 A       │
│ 项目         │
│ P1           │
│ 今天         │
└──────────────┘

┌──────────────┐
│ 任务 B       │
│ 项目         │
│ P2           │
│ 明天         │
└──────────────┘
```

这种布局会迅速产生：

> “Todo Dashboard / Admin Dashboard” 感。

应该使用：

```text
┌─────────────────────────────────────────────────────────┐
│ ○  修复工单分配接口                     项管系统   今天 │
│    工单服务 / 用户中心                  P1              │
├─────────────────────────────────────────────────────────┤
│ ◐  确认供应商测试环境问题               XX项目    等待 │
│    等待张三反馈                         跟进 09/27      │
├─────────────────────────────────────────────────────────┤
│ ○  完成 API Scanner 规则                API平台    P2   │
│    Feign 调用关系扫描                   明天             │
└─────────────────────────────────────────────────────────┘
```

# 6. Sidebar

## 6.1 Sidebar 目标

Sidebar 是导航，不是视觉主体。

必须“安静”。

### 推荐结构

```text
┌────────────────────┐
│ WorkOS             │
│                    │
│  今日              │
│  收件箱        3   │
│  全部事项          │
│  项目              │
│  日报              │
│                    │
│                    │
│                    │
│                    │
│  设置              │
└────────────────────┘
```

---

## 6.2 Sidebar 禁止

禁止：

* 大块彩色导航背景
* 巨大圆角
* 卡片式菜单
* 渐变
* 阴影
* 每个菜单项都有 Badge
* 菜单项高度过高
* 复杂图标
* 动态装饰

---

## 6.3 Active 状态

Active 不使用巨大彩色 Pill。

推荐：

```text
│ 今日
│
▌ 收件箱
│
│ 全部事项
```

使用：

* 左侧 2~3px accent bar
* 极浅背景
* 文字加粗

例如：

```css
.nav-item-active {
  background: #F1F0FF;
  color: #4F46E5;
  font-weight: 600;
}

.nav-item-active::before {
  width: 3px;
}
```

# 7. 页面背景

使用非常浅的灰色：

```css
--color-bg: #F7F8FA;
--color-surface: #FFFFFF;
```

但注意：

> **不要把所有内容都包成白色 Card。**

页面背景应该是：

```text
灰色页面背景
    ↓
白色工作区域
    ↓
列表 / 文档 / 内容
```

而不是：

```text
灰色背景
    ↓
白色 Card
    ↓
白色 Card
    ↓
白色 Card
    ↓
白色 Card
```

# 8. 颜色系统

## 8.1 WorkOS 主色

使用：

```css
--color-primary: #4F46E5;
--color-primary-hover: #4338CA;
--color-primary-light: #EEF2FF;
```

主色只用于：

* Primary Button
* Active Navigation
* Selected
* Focus
* 少量关键强调

```css
--color-border-light: #F0F1F3;
```

## 8.3 Semantic Color

```css
--color-success: #16A34A;
--color-warning: #D97706;
--color-danger: #DC2626;
--color-info: #2563EB;
```

使用原则：

> Semantic color 表达状态，不负责装饰。

# 10. 阴影

阴影只表示“脱离文档流”。

允许：

```text

Modal
Popover
Dropdown
Command Palette
```

不允许：

```text
普通 Item
普通 Section
Sidebar
Page Header
普通 Button
```

不要：

```css
.item:hover {
  box-shadow: ...
}
```

Item Hover 使用背景色：

```css
.item:hover {
  background: #F5F7FA;
}
```

# 12. 页面密度

WorkOS 是工作工具。

不是营销网站。

因此：

> **信息密度必须比普通 SaaS Dashboard 高。**

Item 行高度：

```text
默认：60px 左右
紧凑：52px
复杂信息：68px
```

不要默认 88px / 100px。

# 14. Item Row 状态

## Default

```text
透明 / 页面背景
```

## Hover

```text

```

## Selected

```text

```

## Focus

必须有明显 focus ring：

# 15. Item 操作方式

这是本次重构最重要的交互变化之一。

当前不要坚持：

> 所有修改都必须打开 ItemDrawer。

这会让 WorkOS 变成：

```text
发现事项
→ 打开 Drawer
→ 修改
→ 保存
→ 关闭
→ 找下一个
```

工作效率很差。

---

# 16. Inline Action 原则

高频动作必须可以直接在 Item Row 完成。

至少包括：

```text
完成
开始
恢复
等待
Follow-up
安排今天
```

例如：

```text
○ 完成工单分配接口       项管系统    今天
                         [完成] [更多]
```

Hover 后出现：

```text
✓   等待   跟进   ···
```

# 19. Drawer Primary Action

根据当前状态动态变化。

不要永远：

```text
[保存]
```

应该：

```text
TODO   → 开始
DOING  → 完成
WAITING → 恢复处理
DONE   → 重新打开
```

“编辑”不是用户真正想做的主要动作。

---

# 20. 禁止 Drawer 顶部彩色 Status Strip

不要：

```text

```

用颜色表示状态。

状态应该通过：

```text
icon + label + subtle color
```

表达。

# 31. Inbox 最重要的改变

不要：

```text

→ 点击 Item
→ 打开 Drawer
→ 选择项目
→ 保存
→ 关闭
```

```text

→ Hover
```

# 32. “先都收下”

这是 Inbox 的重要动作。

点击后：

```text

```

但是不要自动：

```text

优先级
计划日期
```

全部由系统猜。

“先都收下”的语义只是：

> 我承认这些事情是我要处理的，先离开捕获状态。

# 89. 最终 Agent 指令

Agent 在实现过程中必须遵守：

> **不要把这次任务理解成“给现有页面换一套 CSS”。**
>
> 这是一次 **WorkOS 工作界面重构**。
>
> 保留：
>
> * 现有业务模型
> * 现有 API
> * 现有路由
> * 现有数据流
> * 现有状态机
> * 现有产品能力
>
> 重构：
>
> * 页面构成
> * 信息层级
> * Item 展示
> * Item 操作
> * Drawer 定位
> * Today 布局
> * Inbox 工作流
> * Project Context
> * Daily 文档体验
> * 视觉系统
> * 交互反馈
>
> 核心目标：
>
> **让 WorkOS 从“管理事项的后台页面”变成“用户打开就知道下一步工作的个人工作驾驶舱”。**
>
> 如果某个视觉效果与信息清晰度发生冲突：
>
> **永远优先信息清晰度。**
>
> 如果某个动画与操作效率发生冲突：
>
> **永远优先操作效率。**
>
> 如果某个设计让页面更漂亮但增加了用户操作步骤：
>
> **不要采用。**
>
> 如果不确定应该做成 Card 还是 List：
>
> **优先 List。**
>
> 如果不确定是否应该打开 Drawer：
>
> **优先 Inline Action。**
>
> 如果不确定是否需要增加一个视觉效果：
>
> **不要增加。**
>
> WorkOS 的设计不是为了让用户“觉得这个页面很酷”。
>
> **而是让用户在工作过程中越来越少思考“这个系统怎么用”。**

这份我建议你**直接替换掉现在那份“Visual & UX Review + Agent Rules”类文档**，不要继续在旧规范上打补丁。

其中我认为最关键的不是颜色，而是三个改变：

1. **`ItemCard → ItemRow`**：从“卡片事项”变成“高密度工作列表”。
2. **`ItemDrawer = 深度编辑，不是所有操作入口`**：完成、开始、等待、跟进、安排日期等高频动作直接在列表完成。
3. **Today 从“六个信息区块”变成“工作驾驶舱”**：左边回答“现在做什么”，右边回答“还有什么上下文不能忘”。

这三个地方改对了，哪怕不做 Dark Mode、不做玻璃、不做 `⌘K`、甚至动画很少，页面也会和现在有**明显的产品级差异**。
