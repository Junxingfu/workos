# 技术设计：以 IDDD 组织 WorkOS

更新：2026-10-17。业务语言与用户规则见[产品与交互](产品与交互.md)，工程约束见[开发规范](开发规范.md)。本文件解释模型及设计决策；字段以 Java 和 Flyway SQL 为准。

## 1. 战略设计：先确定模型边界

主要参考 Vaughn Vernon 的《Implementing Domain-Driven Design》、作者的 [IDDD Samples](https://github.com/VaughnVernon/IDDD_Samples) 和 [Effective Aggregate Design](https://www.dddcommunity.org/wp-content/uploads/files/pdf_articles/Vernon_2011_1.pdf)。参考其小聚合、身份引用、仓储端口和应用编排方式，没有复制示例业务代码。以下边界是 WorkOS 的建模决策。

| 子域 | 业务价值 | 对应模块 |
|---|---|---|
| 个人任务执行（核心） | 一次记录，安排、等待、推动、完成；减少维护成本 | item |
| 项目上下文（支撑） | 恢复目标、重点、进展、阻塞与下一步 | project |
| 工作回顾（支撑） | 保留人工事实，生成可审阅的日报 | worklog、daily |
| 关注与提醒（支撑） | 找出应关注的事实；已读/稍后不改变工作进度 | attention、reminder |
| 工作区偏好（支撑） | 统一业务日和用户偏好 | settings |

当前保留一个“个人工作管理”限界上下文，采用模块化单体。模块不是独立限界上下文，数据库表也不是聚合划分依据。Today、Inbox、Follow-up、Search、浮窗是同一模型的查询入口。Excel 是外部表格语言与本模型间的防腐适配；Tauri、备份、Flyway 属于技术基础设施。account 仅是历史预留表，目前没有身份认证用例，不虚构一个已实现的身份访问上下文。

```text
Excel 文件 → WorkbookPort / ExcelWorkbookAdapter → 批量维护用例
Vue 主窗口、浮窗 → HTTP 适配器 → 个人工作管理上下文
                                      ├─ 任务执行
                                      ├─ 项目上下文 / 工作回顾
                                      └─ 关注提醒 / 工作区偏好
                                 仓储端口 / 查询投影
                                      ↓
                           PostgreSQL 或 SQLite
Tauri 管理本地进程、窗口、会话与数据目录，不决定事项规则
```

将来只有出现不同团队、不同语言或独立发布需求，才重新划分上下文。若把回顾独立出去，任务执行将提供已完成/已记录事实，届时需要公开事件契约、可靠投递和最终一致性设计；当前没有消息队列、事件溯源或跨上下文事件总线。

## 2. 聚合、值对象与不变量

| 模型 | 身份 / 边界 | 负责的行为和不变量 |
|---|---|---|
| `WorkItem` | 事项 ID；内容、状态、计划、等待和项目引用同一版本 | create、revise、transition、plan、unplan、followUp、reorder；笔记能力限制、等待必填、合法流转、复合修订失败不改变原实例 |
| `Project` | 项目 ID；不持有任务集合 | 创建、重命名、归档、恢复；归档不删除任务或关联 |
| `ProjectBrief` | 每项目一份现状，引用项目 ID，独立版本 | 修订目标/重点/进展等；首次保存从 0 升到 1，旧空白页不能覆盖已保存内容 |
| `DailyReport` | 每业务日期一份日报 | write、generate、apply；快照与正文分开，只有确认应用才覆盖正文 |
| `Reminder` | 提醒 ID；独立于事项进度 | schedule、reschedule、dismiss；已处理提醒不能重新延后 |
| `WorkspaceSettings` | 工作区单例，ID=1 | revise；时区、日界线、每周起始和偏好时间先校验再整体变更 |
| `AttentionReceipt` | 稳定关注理由 key | READ / UNREAD / SNOOZE；回执不完成任务、不更改任务日期 |
| `WorkRecord` | 追加的不可变人工事实，由仓储分配记录 ID | 固定记录当时的主项目、业务日、发生时间和正文；不随事项改归属而重写 |

`ItemDetails` 是不可变内容值，校验标题、描述和默认优先级；`ProjectReferences` 去重、排除主项目、限制最多 20 个关联，有关联时必须有主项目；`WaitingPeriod` 区分等谁、何时开始、对方预计时间。这些组合有真正的不变量，不为每个字符串机械建立一个值对象。

事项只保存项目身份，不加载 Project 对象；项目统计不会把全部任务装进 Project 聚合。主项目和关联项目共享一套事项状态和进度。工作记录冻结当时主项目，日报只按该事实归集。聚合的 `State` 是仓储重建与只读输出的快照；外部调用行为方法修改，不能拿 PO 当领域对象。

`TransitionPolicy` 是任务/笔记流转的唯一规则来源，聚合执行和查询 `allowedTransitions` 共用它。计划不是状态；截止、下次跟进、对方预计时间、计划日期是四种不同事实。

## 3. 从目录理解职责和依赖

这里的 DDD 核心是“业务规则由谁保护”，四层目录只是实现它的组织方式。IDDD 不规定必须使用这些 Java 包名。先按业务模块找到事项，再在模块内区分以下四种职责：

| 层 / 包 | 回答的问题 | 事项模块中的例子 | 不应该做什么 |
|---|---|---|---|
| `domain` 领域层 | 这个行为是否合法？会改变哪些事实？ | `WorkItem`、`WaitingPeriod`、`TransitionPolicy`、`WorkItemRepository` | 不读 HTTP 请求，不引用 Spring、PO 或 Mapper |
| `application` 应用层 | 一次用户操作如何完成、如何提交？ | `ItemLifecycleService`、`ItemCommands`、`query.ItemQuery` | 不写 SQL，不把状态规则复制到服务里 |
| `interfaces` 接口层 | 如何接收请求、转换输入、返回结果？ | `ItemController`、`ItemHttpAdapter`、`request.ItemTransitionReq` | 不直接操作数据库，不决定状态流转是否合法 |
| `infrastructure` 基础设施层 | 怎样把模型保存下来、怎样查询展示？ | `MyBatisWorkItemRepository`、`ItemQueries`、`ItemPO`、`ItemMapper` | 不通过修改 PO 绕过聚合的业务行为 |

根目录是 `workos-server/src/main/java/com/workos/`，以 `item` 为学习模板：

```text
item/
  domain/                         一个紧凑的领域模型包
    WorkItem.java                 聚合根：管理一个事项的一致性
    ItemDetails.java              内容值对象，不是接口 DTO
    ProjectReferences.java        主项目及关联项目的身份引用
    WaitingPeriod.java            一段等待的值对象
    TransitionPolicy.java         无状态的流转规则
    WorkItemEvent.java            行为产生的领域事实
    WorkItemRepository.java       存取完整聚合的接口
  application/
    ItemEditingService.java       创建、修订、整理、排序用例
    ItemLifecycleService.java     流转、安排、跟进用例
    ItemCommands.java             用例输入；不是执行服务
    FollowUpJournal.java          追加人工记录的协作端口
    query/                        只读查询接口与筛选条件
    readmodel/                    展示结果、统计行；不能用来保存聚合
  interfaces/
    http/                         Controller 路由与 HttpAdapter 输入转换
    request/                      HTTP 输入格式、校验、显式清空标志
  infrastructure/
    MyBatisWorkItemRepository     仓储实现：重建、版本条件保存、事件落库
    MyBatisFollowUpJournal        人工记录协作端口的实现
    query/                        查询接口实现，可直接查库并批量装配
    mapping/                      MapStruct 查询行到响应的机械转换
    persistence/entity/           PO：数据库列映射
    persistence/mapper/           MyBatis-Plus Mapper 与 SQL 声明
```

**不按每一个 DDD 名词再建目录。** 当前聚合、值对象、策略数量有限，放在同一个 `domain` 包便于一起阅读；多个类不是多个聚合。应用层使用 `*Service` 命名实际用例，`ItemCommands` 等记录类型只表达输入；仓储和协作端口因为有具体替代实现而保留接口。原来的 `interfaces/contract/*Service` 与 `interfaces/facade/*Facade` 已移除，避免一个用例在同名“服务/门面/命令”之间反复跳转。

`HttpAdapter` 是接口层的映射辅助类，接收 Web 请求并构造领域值/用例命令；让 Controller 保持路由可读。它与 Controller 属于同一层，只有具体类，不再套一层门面接口。简单接口可直接调用应用服务，无需为每个 Controller 强造 Adapter。

### 依赖方向与运行调用顺序不同

```text
编译依赖：interfaces → application → domain
          infrastructure → application 的查询/协作端口、domain 的仓储接口
          domain 不引用其他业务层

写请求：Controller → HttpAdapter → Application Service
                                  → 聚合行为 → Repository 接口
                                               ↓ Spring 注入
                                       MyBatis 仓储实现 → Mapper → 数据库

读请求：Controller / HttpAdapter → application.query.*Query 接口
                                    ↓ Spring 注入
                               infrastructure.query.*Queries
                                    → Mapper → 查询视图
```

应用服务调用的是 `WorkItemRepository` 接口；运行时注入 `MyBatisWorkItemRepository`，所以领域不需要反过来依赖 MyBatis。一次操作的关键代码应当能读成：**加载事项 → 检查版本 → 调用业务行为 → 保存事项**。事务由应用服务控制，数据库条件更新处理加载之后仍可能发生的并发修改。

读请求为了显示列表，不需要重建全部聚合。`ItemQueries` 查询 PO 后直接映射 `ItemResp`，再批量补充项目名、最近记录和允许的动作；已删除无意义的 `PO → ItemDTO → ItemResp` 中间层。`ItemProjectDTO`、`LastLogDTO` 等仍是实际 SQL 投影行，不能误读为领域实体。`DailyApplicationService.get` 会创建缺失日报草稿，因此保留在应用用例中，不能伪装成纯读查询。

### 常见类型不要混为一谈

| 类型 | 示例 | 可变性与用途 |
|---|---|---|
| 聚合根 | `WorkItem` | 对外提供业务行为，保护不变量与统一版本 |
| 值对象 | `WaitingPeriod` | 不可变、按值表达含义，构造时验证业务约束 |
| 聚合快照 | `WorkItem.State`、`Project.State` | 仓储重建及只读观察使用；不是外部更新接口 |
| 用例命令 | `ItemCommands.FollowUp` | 表达用户意图与期望版本，不负责执行 |
| HTTP 请求 | `ItemFollowUpActionReq` | 参数校验和接口兼容；由 Adapter 转为命令 |
| 查询条件 / 结果 | `ItemCriteria`、`ItemResp` | 描述筛选与展示，不参与聚合保存 |
| 持久化对象 PO | `ItemPO` | MyBatis 列映射；setter 供存储适配，不是业务修改入口 |

### 各模块怎样套用这个结构

- `item`、`project`、`daily`、`reminder`、`settings`、`worklog`、`attention` 有领域行为，按上述四层组织。`Project` 和 `ProjectBrief` 在同一模块中，但各自是独立版本的聚合。
- `today`、`followup`、`search` 主要提供查询；`inbox` 的批量收下复用事项用例。不创建空的 domain 包，也不把“汇总页面”称为 DDD 聚合。
- `exchange` 协调批量输入，Excel 细节通过 `WorkbookPort` 隔离；`ExchangeStore` 读取事实/记录幂等结果，`ImportBackup` 负责导入前备份。真正写事项仍调用事项用例。
- `common` 是响应、异常、框架配置及时间支持；`shared` 放跨模块共用的少量能力；`desktop` 是本机启动与数据管理。它们不是额外业务子域。

`DomainBoundaryTest` 守住领域无框架依赖、应用层不反向依赖 HTTP 或基础设施、HTTP 不直接依赖基础设施。它只能约束代码依赖；业务边界是否合理仍要看行为测试和产品语言。

## 4. 用例、事件和一致性

### 从一次“对方给了”理解调用链

1. `ItemController → ItemHttpAdapter` 把请求转换为 `ItemCommands.FollowUp`。
2. `ItemLifecycleService.followUp` 开启事务，加载 WorkItem、核对版本并取本次时间。
3. `WorkItem.followUp` 决定目标状态、结束等待并清理本段跟进，产生 `WaitingEnded`、`StatusChanged`、`FollowUpRecorded` 事实，返回需要追加的人工记录正文。
4. `MyBatisWorkItemRepository` 以 `id + version` 更新事项、关联和活动；失败回滚，成功才确认新版本并清空待保存事件。
5. `FollowUpJournal → WorkLogApplicationService` 按事项当前主项目追加人工事实，与本次跟进共同提交。

`WorkItemEvent` 表示已发生的领域事实，仓储适配器将其映射为 `item_activity`。其他聚合尚无跨模块事件消费需求，直接保存其状态；不为满足模式名称制造空事件。Activity 是审计投影，不是事件溯源存储，也不冒充人工工作记录。

### 事务边界

- 通常一个命令修改一个聚合。事项内容/项目引用/状态/计划/事件共同提交；不存在先成功改主项目再失败改关联的半次结果。
- 新建到 Today 原子写入 TODO 与今天的计划；属性修订也经过同一聚合，不能绕过等待和计划校验。
- 项目与现状独立版本；只编辑现状不锁定全部事项。
- 日报生成先读取事实投影，`DailyComposition` 纯领域策略负责按主项目编排，`DailyReport.generate` 只更新快照。
- 设置提交成功后才刷新进程内时区；回滚不能让内存口径与库内设置分离。
- 跟进附带人工记录，以及 Excel 整批成功/整批失败，是明确的本地跨记录事务例外。它们满足用户的原子性要求，不意味着要建一个包含所有事项的大聚合。若将来跨上下文拆分，必须重新设计 outbox/补偿或批量结果协议。

写仓储显式检查受影响行数，冲突不能当成功。MyBatis 默认忽略 null，清空字段由 UpdateWrapper 显式赋 null；设置和提醒本轮补齐 version。部分旧接口允许不带期望版本，但仓储始终按加载的版本条件写入；界面应传编辑开始时的版本，不用后台新版本悄悄覆盖旧草稿。

### Excel 边界

XLSX 由 Apache POI 适配器解析；文件最多 5 MB、展开最多 20 MB、任务最多 2,000 行，拒绝公式。格式库可单独替换，不影响领域行为。

预览保存在进程内，最多 5 个、15 分钟有效；提交重新校验版本和项目。成功批次以规范化行内容 SHA-256 记入 `spreadsheet_import`，与事项变更同事务提交。重复提交返回同一结果，桌面实际导入前保存快照。离开 WAITING 时先执行流转清理，再修订内容，避免产生“等待中但等待对象为空”的非法中间状态。

## 5. 读模型、接口和时间

Today 按 SQL 查询各类事实，再按事项 ID 和产品规定顺序去重；候选最多 5 条。项目筛选以主项目 OR 关联 EXISTS 避免分页放大；统计用归属 UNION 后聚合。关联展示批量装配。

`AttentionPolicy` 根据有效任务生成关注理由，key 为类型＋事项 ID＋事实日期/时间；同一逾期已读后不每日重复产生新理由。失效理由不再展示。

`TaskOverviewQuery` 返回 TODO / DOING / WAITING 三类完整计数及选中状态前 30 条，按优先级、更新时间、ID 排序。摘要复用 ItemQueries，包含主/关联项目、计划、截止、跟进、等待天数、最近记录和剩余步骤；全部业务标记由后端计算。

接口根路径 `/api`，统一 `BaseResponse<T>`；code=0 成功，业务失败通常 HTTP 200，客户端必须判断 code/message。Long ID 序列化为字符串；数量在 API 边界转 number，ID 不转数字。分页为 total/pageNo/pageSize/dataList。

| 能力 | 接口入口 |
|---|---|
| Today / Inbox | `/today`、`/today/plan/reorder`；`/inbox`、`/inbox/accept-all` |
| 事项 | `/items`、`/items/quick-capture`、`/items/{id}` |
| 事项行为 | `/items/{id}/transitions`、`follow-up-actions`、`plan`、`activities` |
| 项目与现状 | `/projects`、`/projects/{id}`、`archive`、`restore`、`context` |
| 工作记录与日报 | `/work-logs`；`/dailies/{date}`、`generate`、`apply-generated`；`/dailies?weekStart=` |
| 提醒、设置、搜索 | `/reminders`、`/reminders/pending`、`/reminders/{id}/dismiss`；`/settings`、`/search`、`/follow-ups` |
| Excel | GET `/exchange/tasks?template=`；POST `/exchange/tasks/preview`（multipart file）、`/exchange/tasks/apply`（token） |
| 通知与浮窗 | GET/POST `/attention`（key/action）；GET `/items/overview?status=TODO\|DOING\|WAITING` |
| 桌面数据 | `/desktop/storage`、`backup`、`import`、`restore` |

完整 HTTP 方法和输入约束以 Controller/Swagger 为准。状态只走 transitions，通用属性更新没有 status；空值通常表示不修改，清空通过 clearProject/clearDueAt/clearNextFollowUp，关联 `[]` 表示清空、null 表示不改。

PostgreSQL 用 TIMESTAMPTZ / DATE；SQLite 用 epoch 毫秒 / ISO 日期文本，由 TypeHandler 保持 Instant/LocalDate 契约。API 时间点为 ISO Instant；`TimeZoneHolder` 读取工作区时区和日界线计算业务日，默认 Asia/Shanghai 与 0 点。界面尚未开放设置页，不把服务器配置能力误说成可见产品功能。

前端页面通过 `api/index.ts → api/client.ts` 请求。ItemCard 只发动作，ItemDrawer 管编辑草稿与离开保护，ItemStateFlow 只显示 allowedTransitions。useListActions 管忙碌与撤销，useCaptureRefresh 通知各窗口重读。写后重新 GET，较旧响应不得覆盖新筛选。

## 6. DDL 与 Flyway

唯一结构来源：`workos-server/src/main/resources/db/migration/`。删除旧手工 init SQL 和桌面 schema 副本，Docker 只创建数据库，Spring 启动时统一迁移。

| 模式 | 版本序列 |
|---|---|
| PostgreSQL | V1 初始表 → V2 关联项目 → V3 通知/导入账本 → V4 聚合版本及表/列注释 |
| SQLite | V1 初始表（含关联） → V2 通知/导入账本 → V3 聚合版本及注释元数据 |

Flyway 版本由 Spring Boot BOM 管理。自定义 `DatabaseMigrations` bean 先识别旧库再执行 migrate，关闭 Boot 的第二个自动初始化器；`cleanDisabled=true`、`baselineOnMigrate=false`。没有历史表时，只接管已知完整的旧 WorkOS 表集合，建立对应基线再升级；缺表、组合不完整、未来 SQLite 版本会拒绝启动。旧版本原有字段若已被人工改坏，后续 SQL/约束仍可能拒绝，不能把表集合识别理解成任意旧库修复工具。

SQLite 接管前 `VACUUM INTO` 保存 `before-flyway-*` 快照；已有 Flyway 库有待升级项时保存 `before-migration-*`。Flyway 历史负责迁移与校验和，`PRAGMA user_version=3` 保留为桌面备份兼容标记。新库直接执行全部迁移；重启不重复执行；已发布迁移不可修改，只能追加版本。

PostgreSQL 使用原生 COMMENT ON TABLE/COLUMN；SQLite 不支持该语法，使用 `schema_comment(table_name,column_name,description)` 保存可查询的领域注释（空 column_name 表示表）。SQL 内同时解释迁移意图，PO 注释说明存储含义。

| 表 / 结构 | 归属 |
|---|---|
| item、item_project_link | WorkItem 聚合的持久化表示 |
| item_activity | 领域事件的同步审计投影 |
| project、project_context | Project、ProjectBrief 两个独立聚合 |
| work_log、daily | 人工工作事实、日报聚合 |
| reminder、attention_receipt | 手动提醒、关注理由回执 |
| settings | WorkspaceSettings 单例 |
| spreadsheet_import | 批次提交幂等账本 |
| account | 历史身份预留；尚无认证能力 |
| flyway_schema_history、schema_comment | 技术迁移历史和 SQLite 注释元数据 |

完整备份/恢复保留业务表；旧备份缺少新表时置空，旧 settings/reminder 没有 version 时用新结构默认值。恢复不覆盖当前迁移历史和注释表。禁止删除数据卷来“完成升级”；PostgreSQL 升级前由运行者 pg_dump，具体命令见运行手册。

## 7. 桌面与浮窗

Tauri 2 打包 Vue、Java 17 jlink 运行时和共享后端。启动原生进程 → Java → 数据库锁/Flyway → 自动备份 → ready.json → 本地页面。Java 监听 127.0.0.1 随机端口，随机密钥换取 HttpOnly/SameSite Cookie，校验 Host/Origin/会话；前端没有通用 Tauri 文件或命令权限。

关闭窗口隐藏，退出应用停止 Java；父进程消失时 Java 自行退出，异常退出最多自动重启 3 次。休眠时应用暂停，唤醒后重新读取；不承诺崩溃后恢复未提交输入。数据位于用户目录，替换应用包不会覆盖数据库；单工作区文件锁、SQLite WAL、外键、单连接写事务继续保留。

浮窗设计参考 [macOS 便笺的置顶与半透明](https://support.apple.com/guide/stickies/welcome/mac) 和任务小组件的摘要入口；只借鉴交互，不复制资产。圆角与半透明仅用于桌面悬浮层，主应用仍用紧凑工作界面。

- 原生透明无标题栏窗口，置顶、跨桌面；默认收起 280×76，展开 380×520。
- X 隐藏浮窗，应用菜单/状态栏可重开；展开/收起和 Esc 不退出应用。
- 外观滑杆调背景不透明度 35%–100%，文字保持不透明。偏好写入工作区 `widget-preferences.json`，不依赖随机端口的 localStorage。
- 展开可调整大小，范围 300×300 至 900×1000；右下角手柄捕获屏幕位移，macOS 不依赖未实现的原生 resize-drag。手柄聚焦后方向键每次调整 20px。调整结束和收起保存尺寸，靠近屏幕边缘会限制位置。
- 点击任务向主窗口发送固定的事项打开事件，路由进入 `/items?itemId=`；不直接刷新主窗口，切换前遵守未保存草稿保护。
- 每 30 秒、窗口聚焦及成功写入后重读。错误明确提示，不把断连显示成 0。浏览器 `/focus` 为预览，不具备系统置顶/透明/调整原生窗口能力。

桌面备份通过 `VACUUM INTO` 产生一致快照；跨库迁移从本机允许的 PostgreSQL 来源用只读事务复制，SQLite 目标以事务接收并核对，源库不改。数据库管理适配器允许 JDBC，业务 CRUD 统一 MyBatis-Plus。

## 8. 初学者阅读顺序与设计取舍

先沿一个用例阅读，不必一次看完全部模块。建议从“等待的资料已经收到”开始：

1. [ItemLifecycleService](../workos-server/src/main/java/com/workos/item/application/ItemLifecycleService.java) 的 `followUp`：看版本检查、加载、调用、保存、追加人工记录这五步。
2. [WorkItem](../workos-server/src/main/java/com/workos/item/domain/WorkItem.java) 的 `followUp / transition`：看哪些字段必须一起改变、为什么离开等待要清理本段跟进。
3. [WorkItemRepository](../workos-server/src/main/java/com/workos/item/domain/WorkItemRepository.java) 与 [MyBatisWorkItemRepository](../workos-server/src/main/java/com/workos/item/infrastructure/MyBatisWorkItemRepository.java)：对比业务存取契约和 SQL/版本/事件落库实现。
4. [ItemHttpAdapter](../workos-server/src/main/java/com/workos/item/interfaces/http/ItemHttpAdapter.java) 与 [ItemQueries](../workos-server/src/main/java/com/workos/item/infrastructure/query/ItemQueries.java)：看请求如何成为命令、执行后如何重新读取视图。
5. [WorkItemDomainTest](../workos-server/src/test/java/com/workos/WorkItemDomainTest.java)：在没有 Spring 和数据库的情况下验证规则。再看 `AggregateBehaviorTest` 中其他聚合的例子。

理解这一条后，再读 `DailyComposition → DailyReport → DailyApplicationService`，体会“读事实、按业务规则组合、写快照”的区别；最后读 `TaskExchangeService` 及三个端口，理解防腐适配和批量事务例外。

几个需要保留判断的地方：

- 单体内有共享数据库和跨模块查询，不等于已经实现多个自治限界上下文。不能把包搬到独立服务就认为可以独立运行。
- 一般每事务修改一个聚合；跟进附带记录和批量导入遵循明确的产品原子性要求，使用本地跨聚合事务。将来拆上下文时必须重新设计这些边界。
- `State` 快照是本项目的持久化适配选择，不是 IDDD 要求的固定模式。`WorkItem` 的仅生命周期构造用于规则预演，正式保存必须有内容；其他聚合使用完整 State 重建。
- `@Transactional`、MyBatis-Plus、Google Java Style、Flyway 分别处理事务、存储、可读性、结构演进，不是 DDD 本身。禁止 `var` 是本项目的明确类型约定，不冒充 Google 的规则。

新增行为先回答：属于哪个聚合、保护什么不变量、失败应回滚到什么边界，再决定放哪个类。不要为符合目录形状增加没有职责的接口、DTO 或服务。
