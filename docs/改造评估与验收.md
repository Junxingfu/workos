# WorkOS 可用性改造评估与验收

日期：2026-10-11。范围：记录 → 收下/待办 → 安排今天 → 开始/等待/完成，以及直接影响这条路径的数据一致性。

## 需求依据

- `1-WorkOS MVP 产品需求文档.md` 是业务需求基线。产品定位、领域对象及任务状态保留。
- `2-WorkOS MVP 研发设计文档.md` 和 `3-WorkOS MVP 数据库、API 与页面详细设计.md` 提供研发契约。
- `archive/DESIGN.md` 是历史视觉规范，文档自己明确“本文不是业务 PRD”。现行前端约束见 `archive/前端规范.md`。
- 冻结规则允许因用户可用性测试阻断、需求矛盾、逻辑漏洞和数据一致性问题修订。这次用户实际反馈：记录麻烦、快捷键不好用、状态流转混乱、不知道如何让事项到今天页，无法继续使用。

## 评估结论

产品的核心定位成立，但实现让用户承担了过多的流程知识：用户必须知道收件箱、待办、优先级和计划日期之间的关系，才能把一句工作安排变成今天可执行的任务。界面又隐藏了主要动作，没有把这一关系教给用户。

| 阻断 | 原因与证据 | 本次处理 |
|---|---|---|
| 记录后看不到事项 | 快速记录固定进 INBOX；P2 收下后不进 Today 决策队列，且没有清楚的安排入口 | 全局鼠标记录入口；今天页直接记录到计划；其他地方可选待办或待整理；成功后刷新当前列表 |
| 不知道今天从哪来 | 普通事项只有打开抽屉选日期；Today 空态让人去“还没安排”，但这里只能看到 P0/P1 | 普通待办也进入待安排候选，保留 5 条上限；显式“从全部待办选择”；全部事项行内安排今天 |
| 状态操作混乱 | TODO 的主要动作是完成；状态只显示符号；抽屉的 INBOX 没有主要收下按钮 | 显示状态中文；待办以开始为主，同时允许直接完成；待整理显示收下；抽屉同样遵守这些语义 |
| 等待动作绕路 | 点等待先开完整抽屉，再开等待表单 | 行内等待/跟进直接打开相关小表单；详情仍能查看和深度编辑 |
| 昨日计划消失 | 非计划分区均要求 planned_date IS NULL，旧计划只有计数没有记录 | 返回并显示未完成的旧计划，可重新安排；绝不自动结转 |
| 已有计划遮挡风险 | 未来计划排除了逾期、到期、到点跟进及等待查询 | 计划日期不再屏蔽这些事实，后端按分区顺序去重 |
| 批量收下改坏数据 | 全量重置优先级；指定 ID 还清项目；给此前的 TODO 写假的收下活动 | 通过事项生命周期 Module 的统一 Interface，只收下本次 INBOX 集合，保留已填写属性 |
| 笔记只能取消 | 通用状态机与 NOTE 能力矩阵交集没有正常保存动作 | NOTE 收下为已归档，恢复为待整理，不进入任务执行流和日报 |
| 已解决跟进仍报错/再次出现 | DOING→DOING 被拒绝；TODO→DOING 未清跟进时间 | 相同状态不重复转换，跟进结果与清跟进时间在同一事务里完成 |
| 项目归属清不掉 | null 表示不修改，而前端把 null 当清空 | 增加显式 clearProject/clearDueAt；空值清除和版本冲突均由后端处理 |
| 输入被带到另一事项、关闭丢记录 | 抽屉复用旧草稿，未提交工作记录没有关闭保护 | 新事项重置上下文；同一事项刷新保留编辑；关闭/离开保护未保存输入 |
| 事项超过 50 条无法找到 | 页面固定第一页，无分页 | 增加分页、待整理/取消筛选、未分类筛选；防止迟到搜索响应覆盖新结果 |
| 项目里的待办无法找到 | 项目详情仅查进行中和等待中 | 加入待办列表和查看项目全部事项入口；刷新不覆盖正在编辑的现状 |
| 日报生成后无法应用 | 生成更新了版本，响应未返回新版本 | 返回并采用最新版本；生成保留正文，应用才覆盖 |

## 明确修订的默认行为

以下调整是基于本次实际阻断，有意改变冻结基线的局部规则；基线原文保留，本文件记录差异：

1. 快速记录仍只要求标题，但允许显式选去向。全局入口默认待整理，今天页入口默认今天做。TODAY 在一个后端事务内生成 TODO 与业务日计划，无须先收下再安排。未提交的记录表单关闭后保留草稿。
2. Today 的“还没安排”从仅 P0/P1 扩展为未计划的 TODO/DOING TASK，仍按用户优先级、截止时间排序、最多 5 条。它只是候选区，不把候选自动加入今日计划；更多事项通过全部待办选择。
3. 逾期/到期/跟进/等待不再要求无计划日期，已在前序分区中的事项仍不重复展示。旧计划作为补充列表展示，不自动结转。
4. 批量收下保留用户已填项目与优先级。没有主动填写时仍使用原有 P2/无项目默认值。
5. 浏览器快捷键改为 ⌘/Ctrl + Shift + K。原 Alt + Space 在部分系统与输入法环境冲突；当前仓库是 Web 实现，不承诺桌面级全局快捷键。鼠标入口始终可见。
6. 高频行内动作常驻可见；不再要求用户悬停后才发现按钮。字号、列表密度与技术栈保留。
7. NOTE 的类型专属生命周期补齐：待整理→归档/取消；归档/取消→待整理。TASK 状态机不变。

## 操作语义

- 待整理：尚未决定是否要做。点收下变成待办，不要求项目或日期。
- 待办：决定要做，尚未开始。点开始进入进行中；已做完也可直接点完成。
- 今天：计划维度，独立于状态。安排今天不会擅自开始工作，也不会把等待中的事自动恢复。
- 等待中：在等别人；只填写等谁及可选时间。恢复处理结束这段等待。
- 跟进：处理一次跟进结果；不是第三种事项类型。
- 已完成/已取消：关闭任务，可按后端允许的转换重新打开。

状态允许值始终来自后端 allowedTransitions。状态变更仍只走 transitions。每次写操作后重新 GET，前端不模拟成功状态。

## 工程取舍

捕获行为集中在 QuickCapture Module，三个页面入口共用同一 Interface，减少 Locality 分散。Today 查询与去重留在后端，不让各页面自己猜事项的归属。批量收下复用生命周期 Interface，使 NOTE、TASK、版本检查与活动历史保持一致。未新增状态管理库、业务对象或一级导航；无需数据库结构迁移。

## 回归验证

`workos-server/src/test/java/com/workos/WorkflowIntegrationTest.java` 通过真实 Spring 业务入口和 PostgreSQL 验证以下 9 个用例，每例事务回滚：

1. 直接记录到今天，开始并完成。
2. 收件箱普通 P2 任务收下，候选可见，安排到业务日今天。
3. 以前未完成计划仍可见，并能重新安排。
4. 未来计划不屏蔽逾期及跟进，互斥分区不重复展示。
5. 进行中任务解决跟进，保留状态并清跟进时间。
6. 批量收下保留项目/优先级，只给实际收下对象记历史。
7. 显式清空截止时间，并拒绝过期版本。
8. 笔记归档/恢复，不进日报；恢复清完成时间。
9. 日报生成→应用使用新版本，生成不覆盖草稿，旧版本应用被拒绝。

运行需要专用验收数据库（已初始化），设置 WORKOS_INTEGRATION_TEST=true 和 DB_NAME；默认运行跳过数据库集成测试，避免意外连接工作库。可用 `mvn test`，要求 Maven 自身运行在 JDK 17，不能只把 javac 指向 JDK 17。

2026-10-11 验证结果：

- 在独立 PostgreSQL 数据库 `workos_usability_20261011` 运行上述集成测试：9 个通过，0 失败，0 错误，0 跳过。测试库与 `workos` 工作库隔离。
- `npm run build` 通过，包含 TypeScript 检查。原拦截器返回类型和 Node 类型声明错误均已修复；仍有现有主包超过 500 KB 的构建提示，本轮未做依赖拆包。
- 浏览器走通：今天页一句话记录→开始→完成；收件箱记录→收下→候选→安排今天→等待→对方给了→进行中；日报生成→应用；项目待办→查看项目全部事项。
- 浏览器验证了 ⌘+Shift+K、记录浮窗关闭后保留草稿、未提交工作记录关闭提示并继续编辑、37 条数据的分页及长标题。正常操作期间未捕获到控制台 error；主动停服务时 Today 显示错误与重试入口，不伪装成空列表。
- 检查 1280×800、1440×900、1728×1117 和 1080 宽度无横向溢出，事项行高 52–60 px；1024、853 的等效可用宽度也无横向溢出。后两项模拟 1280 宽屏在 125%/150% 缩放下的可用空间，未声称完成浏览器原生缩放验证。
- 验收后服务切回 `workos` 工作库；独立验收库保留测试记录，便于复查。无表结构迁移，也未向工作库写入验收数据。
